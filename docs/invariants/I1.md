# I1: Spirits cannot bypass the Capability Registry

See Architecture §3.2 for the full invariant definition and rationale.

## Enforcement Mechanism (v0.1-α type codification)

Type-level codification lives at `crates/maos-domain/src/invariants/i1.rs`:
the `InvariantI1` marker type anchors I1 in the type system. Runtime enforcement
ships in future stories per Architecture §3.2.1; at v0.1-α the type codification is
the structural enforcement anchor.

See Story 1a.1 for the type-codification rationale; Architecture §3.2 + §3.2.1
for the full enforcement matrix.

## v0.1-β runtime anchor

Story 1b.2 lands the Capability Registry runtime body:
`crates/maos-kernel-core/src/capability/{cap_tokens, cap_policy, cap_audit, cap_quota}/`.
The `CapabilityRegistryAdapter` composite mediates every external call through
`issue → verify → audit` with TOCTOU re-validation (NFR-Maint-8) and
lock-free shard-ring verify (ADR-030 <5µs P99).

## v0.1-β sandbox enforcement anchor

Story 1b.3 makes capability mediation enforceable via OS-level sandboxing.
Sandbox tiers T0/T1/T2 enforce per-Spirit restrictions at the kernel boundary:
- Linux: Landlock (filesystem) + seccomp-bpf (syscall allow-list) + cgroups v2 (resource caps)
- macOS: Seatbelt SBPL (filesystem) + setrlimit (resource caps)
- Windows: fail-closed stub (SandboxUnavailable until CreateRestrictedToken ships)

`SecurityManagerAdapter::admit_spirit` computes the effective tier via
`strictest_of(manifest, trust_tier, operator_policy)` and rejects T3+ at v0.1-β.
`spawn_sandboxed` applies the enforcement at process spawn time.
Runtime body: `crates/maos-kernel-core/src/security/sandbox/`
