# I9: The kernel itself stores no secrets and learns no patterns

See Architecture §3.2 for the full invariant definition and rationale.

## Enforcement Mechanism (v0.1-alpha)

The `cargo xtask check-empty-kernel` lint mechanically enforces I9 at PR-merge time.

- **Whitelist:** Persistent state is permitted only inside three sanctioned holder paths:
  1. `crates/maos-kernel-core/src/journal/`
  2. `crates/maos-kernel-core/src/iac/transparency_log.rs`
  3. `crates/maos-kernel-core/src/capability/cap_tokens/`

- **Denylist:** Any struct field whose type matches the persistent-state denylist
  (e.g., `HashMap`, `Mutex`, `Vec<NonPrimitive>`) outside the whitelist triggers a
  build failure with the literal message:
  `I9 violation: persistent struct <StructName> not in I9 whitelist at <file>:<line> (field: <field_name>: <denylisted_type>)`.

- **Exemption attribute:** `#[i9_exempt(reason = "...")]` on a struct skips the
  denylist check for that struct, but the exemption site must be enumerated in
  `docs/invariants/i9-exemptions.md` with a one-paragraph rationale signed by ≥2
  maintainers. Missing enumeration fails the gate.

- **Back-link:** This enforcement mechanism was introduced in Story 0.2
  (Epic 0: Quality Substrate).

## Enforcement Mechanism (v0.1-α type codification)

Type-level codification lives at `crates/maos-domain/src/invariants/i9.rs`:
the `InvariantI9` marker type anchors I9 in the type system. Runtime enforcement
ships in future stories per Architecture §3.2.1; at v0.1-α the type codification is
the structural enforcement anchor.

See Story 1a.1 for the type-codification rationale; Architecture §3.2 + §3.2.1
for the full enforcement matrix.
