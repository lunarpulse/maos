# MAOS v1.0.0 — release notes (general availability)

Every statement below is traced to a file in this repository. Nothing here was verified on a stable
performance runner or against production vendor keys. The hosted run ids for the frozen candidate SHA
(discipline `aggregate` and `release-ready`, the T3 fuzz chain, the counting `release.yml` rehearsal, the
publication run) are **recorded in the post-tag record commit**, never in this file: the notes ship inside the
tagged commit and cannot cite runs that happen after it is frozen.

## 1. What this release is

`v1.0.0` is the first **general-availability** release of MAOS. It is a normal (not pre-release) GitHub release
and is `latest`. It follows the unpublished `v1.0.0-rc.1` tag and the published `v1.0.0-rc.2`
([`v1.0.0-rc.2.md`](v1.0.0-rc.2.md)). The 1-year LTS commitment (NFR-Maint-6) **starts at this tag's commit**
([`lts-policy.md`](lts-policy.md)); security-only patches follow after year 1, and no end-of-support date is
claimed. The release contract is [`STABILITY.md`](../../STABILITY.md).

### Scope

GA covers Epics 1-21 as defined in the session roadmap (`_bmad-output/planning-artifacts/session-roadmap-2026-11-16.md`,
Stage 3): the Epic 20 release exit and the Epic 21 product stories that the 2026-11-13 correct-course left in the GA
set: `21-3` durable A2A pin store and `GET /v1/a2a/pins` (AC1 only), `21-6` memory-tier quota enforcement (FR28),
`21-7` production consent granter and gate (FR29), `21-9` the WASM host on by default (narrowed), `21-10` the
I1-I14 invariant ledger, `21-12` attestation and credential defects, `later-registry-quarantine-closure`, plus the
reasoning-model adapter usage fixes (`27-2`) and the Spirit evaluation stories `28-1`/`28-2`. The default artifact
carries the Wasmtime engine (an explicit engine-free build remains supported).

### What the release does not claim (summary)

The precise, per-row list is [`RELEASE-HOLDS.md`](../../RELEASE-HOLDS.md) (sections "Claim boundaries — Holds 1–2",
"Claim boundaries — v1.0.0 scope", and the GA-tag procedure). Section 3 below restates each row on one line. A
boundary is violated by over-claiming, not by shipping.

**No external penetration test was performed; no ECCN determination was made; assurance is AI-agent review plus the hermetic CI proof only.**
Neither NFR-Sec-7 nor NFR-Comp-1 is claimed met. The default artifact carries the Wasmtime engine; it is not
classified and not counsel-cleared (`RELEASE-HOLDS.md` GA-tag procedure item 3,
[`docs/compliance/export-counsel-precondition.md`](../compliance/export-counsel-precondition.md)).

Labels read by the release workflow and by operators (each alone on its line, verbatim):

Perf verdicts: ABSENT
Release environment protection: NOT PROVISIONED

- `Perf verdicts: ABSENT`: no NFR-Perf timing figure was measured on a stable runner, and none is claimed
  (`RELEASE-HOLDS.md` boundary 3; `release.yml` accepts ABSENT for GA and refuses a GA notes file without the line).
- `Release environment protection: NOT PROVISIONED`: the GitHub `release` environment has no required reviewers
  and no tag restrictions (`docs/runbooks/provisioning-checklist.md`, row `release environment protection evidence`
  = `absent`). "Only the key holder tags" is operator policy, not an enforced control: pushing the tag triggers
  CI-held artifact signing, and no Git tag signature is created or verified.

### Invariant claim

All 14 kernel invariants (`docs/invariants/I1.md` ... `I14.md`) carry `claim: asserted`, each with an executing,
non-claiming CI witness. **None is claimed `guaranteed`**; this release does not state a 14/14 guarantee. The
witness gaps that keep each row at `asserted` are written in the row files and in
`docs/invariants/README.md` ("No row is currently guaranteed"); the I5 FR13 quarantine fence and the I9/I14 owner
notes are among them.

## 2. Supported platforms and artifacts

Binaries (`release.yml` builds five per target: `maos`, `maosctl`, `maos-registry-server`, `maos-spirit`,
`maos-wasm-runner`): `linux-amd64` (`x86_64-unknown-linux-gnu`), `linux-arm64` (`aarch64-unknown-linux-gnu`),
`darwin-arm64` (`aarch64-apple-darwin`). Signed `SHA256SUMS`/`SHA256SUMS.sig`; amd64/arm64 `.deb` and `.rpm` with an
independently signed `SHA256SUMS-packages`/`.sig`; rendered `maos.rb`, `PKGBUILD`, `maos.spec`,
`debian-recipes.tar.gz` and `verify-release.py`. Windows is not a release target
([`windows-deferral.md`](windows-deferral.md)). The container image is built and smoke-tested by `container.yml`;
it is **not** pushed to Docker Hub (no credentials are provisioned).

Not claimed: Docker Hub image push and cosign signature; Homebrew tap and AUR publication (the rendered recipes are
attached to the release, never copied to a tap or AUR by this release); Windows; the live-key and external legs
(live-key J0 leg, live Worker under the 17-1 profile, nightly cassette re-record, J1 live signed take, J4 live
recording, live Gemini and Kimi vendor round trips, RPO/RTO production proof, external-author cohort). The package
signatures were verified by the release pipeline's own self-check; an independent verification of the package
signatures is not claimed.

### Approved carry-over boundaries (Epic 21 closure matrix, 2026-11-23)

Source: `_bmad-output/planning-artifacts/epic-21-closure-matrix-2026-11-23.md`, "Carry-over candidates", as approved
by the operator on 2026-11-23. These are documented limits of `v1.0.0`:

- **21-7 consent:** after a hot swap that auto-reverts, the predecessor's consent declaration is not restored; the
  declaration in force is the successor's, which a swap may only keep or narrow (F6-revert). `[consent.recall]` is
  additive at every manifest schema and its recipient IDs are not roster-validated at admission (F4). Guests observe a
  consent refusal as `IntentAllowlistMismatch`; no dedicated WIT variant yet (F7). Cross-incarnation retract is
  best-effort across a post-commit delivery failure (F3 residual). Consent is a recall/fetch restriction on the log;
  it does not hide a frame already delivered to the recipient's session (F8, `docs/adr/ADR-012`).
- **21-9 WASM host:** installed-Spirit boot trusts the on-disk package publisher; a writer to the registry root is
  outside the guarantee (H1, M1-M5).
- **21-6 memory quota:** enforced on the private and shared tiers only (collective tier: `v25-reza-postgres-legs`);
  halt context text is retained in approval-log `reasoning`.
- **21-12 forget completion:** forward-converging, not atomic; the intent frame retains the free-form reason;
  boot-time regeneration requests are not dispatched (M3/M7/M8, `v25-erasure-crash-reconciliation`).
- **21-3 durable pins:** the pin file is not integrity-protected against a local writer with the operator's file
  permissions, and a failed fence write leaves restart unprotected.
- **21-10 lock gate:** `invariant-lock` runs from the PR's own revision until it is moved to a protected revision.

### Operator-facing known limits

- **Host-config split.** State directories can resolve to different roots when `MAOS_HOME` is unset; the release does
  not claim a single data root. Set `MAOS_HOME` explicitly in production (residual dispositions OQ-6/OQ-8/OQ-9,
  `_bmad-output/planning-artifacts/epic-21-residual-dispositions-2026-11-23.md`).
- **Pin file name.** The durable A2A pin file is per host: `a2a-pins-<hex(local_host)>.json` under the state
  directory, so several daemons can share one `MAOS_HOME`; it is **not** a single `a2a-pins.json`. A daemon holds the
  pin-file lock for its lifetime; a second opener of the same file is refused until the first exits.
- **Worker workspaces are not size-capped** (`RELEASE-HOLDS.md` row 20): a runaway Worker can fill the filesystem
  that holds the workspaces root.
- **Release hygiene.** The `release` environment is not protected (label above); a tag push publishes.

## 6. Known issues found after release (2026-11-25)

**Collective rows can be written unencrypted when the at-rest key is unusable.** This affects `v1.0.0` and every
release before the fix.

- **When it happens.** All of these hold: you run the Host in the default build; the Collective tier is on
  (`MAOS_LOOM_POSTGRES` and `MAOS_LOOM_HOME_TEAM` are set); at least one `MAOS_KMS_*` variable is set; and
  `MAOS_KMS_MASTER_KEY` is missing, is not valid hex, is not 32 bytes, or is all zero. In `v1.0.0` the master key
  is the only KMS, so "down" means "the key is unusable", not a network outage.
- **What goes wrong.** The Host still starts, and its startup line still reports `kms=true`, but the Collective
  store writes its rows without encryption. Only the Collective store value column is affected.
- **What is not affected.** Hosts with no `MAOS_KMS_*` variable (the documented default is plaintext); Hosts
  with a valid master key (rows are sealed, and a seal failure refuses the write); the cohort daemon, which
  refuses to start in this state; every store other than the Collective store.
- **Workaround.** Do not start the Host with `MAOS_KMS_*` set unless `MAOS_KMS_MASTER_KEY` is a valid, non-zero,
  64-hex-character key; verify the key before boot and remove stray `MAOS_KMS_*` variables. Restarting with a
  corrected key seals new writes; rows already written in plaintext stay plaintext until you rewrite them.
- **Fix.** Story `23-8-external-kms` (decision D-23-8-07 A): the seal hook always exists when KMS is configured,
  an invalid KMS configuration refuses to boot, and an unreachable KMS refuses writes instead of writing
  plaintext. It is not part of `v1.0.0`.

This is claim boundary row 22 in `RELEASE-HOLDS.md`.
