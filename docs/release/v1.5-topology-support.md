# v1.5 Topology Support — Ops-Honesty Statement (Story 10.4b / Task 3.1)

**v1.5 supported topology: 2-Host bilateral pair. 14-institution Cortex / 25-host churn = v2.0, NOT YET SUPPORTED.**

## What v1.5 ships

At v1.5 the only supported multi-Host topology is the **2-Host bilateral pair**:
one prod-edge Host (Mira-class diagnostic) ↔ one dev-environment Host
(Nash-class architect), joined over the live A2A JSON-RPC-over-mTLS/TCP
transport (FR23b, Story 8.6) with pre-paired peer cert fingerprints (TOFU
pinned) and ADR-012 typed-intent consent allowlists.

- Reference pair: Mira (Host A) + Nash (Host B).
- Deployment manifest: `spirits/topologies/bilateral-2-host-mira-nash.toml`.
- Live bilateral proof: `crates/maos-a2a-tcp/tests` (real mTLS handshake,
  consent-gated advisory routing, rotation drill) +
  `spirits/mira/tests/halt_bilateral.rs` (halt → mobile-push + A2A advisory).

## What v1.5 does NOT ship (deferred to v2.0)

The 14-institution Cortex / 25-host churn topology is **v2.0 scope and is NOT
supported at v1.5**. Specifically, v1.5 has:

- No multi-Host fan-out beyond the bilateral pair (no N-way Cortex).
- No 25-host membership-churn / dynamic-join protocol.
- No cross-Host broadcast beyond the paired advisory.

An operator who needs N-way topology must wait for v2.0. This is a deliberate
scope boundary (architecture §6.4 / §13.1 J4), not a defect.

## Why

The bilateral pair is the smallest topology that exercises every load-bearing
cross-Host primitive (mTLS pairing, TOFU pinning, typed-intent consent, halt
fan-out to mobile push, rotation). Proving it end-to-end first de-risks the
N-way generalization without shipping an undertested 25-host protocol at v1.5.
