# Manifest 스키마 v5 (현재)

스키마 v5는 `wasm-component` form, 필수 `[class].artifact` 경로, 그리고 `[capabilities.required.iac]` 및 `[capabilities.required.log]` 선언을 추가합니다. 권위 있는 값은 `maos-spirit-abi`의 `MANIFEST_SCHEMA_VERSION = 5`입니다.

## WASM component class 선언

WASM component Spirit는 정확히 하나의 form인 `wasm-component`와 상대 `.wasm` artifact 경로를 선언합니다. 경로는 launch 경로가 manifest 디렉터리를 기준으로 해석하며, 스키마 검증은 artifact를 열지 않습니다.

```toml
[class]
name = "third-party-component"
version = "0.1.0"
abi = "1.0"
manifest_schema_version = 5
min_substrate_version = "0.1.0"
forms = ["wasm-component"]
artifact = "dist/spirit.wasm"
trust_tier = "local"
description = "A component-model Spirit"

[sandbox]
tier = "T2"
```

`wasm-component`는 다른 form과 결합할 수 없습니다. schema v5와 `artifact`가 필요하며, 다른 모든 form은 `artifact`를 금지합니다. artifact 경로는 비어 있지 않은 상대 경로여야 하고, 최대 4096바이트이며, `..` segment가 없고 `.wasm`으로 끝나야 합니다.

## IAC send capability

`[capabilities.required.iac]`는 Spirit가 bus frame을 보낼 수 있는 peer class를 선언합니다. `send`는 닫힌 집합의 항목만 받습니다.

- `"broadcast"` — `to` 목록이 비어 있는 frame.
- `"spirit:peer"` — 하나 이상의 Spirit에게 주소가 지정된 frame.

```toml
[capabilities.required.iac]
send = ["spirit:peer"]
```

`send`가 있으면 비어 있지 않아야 하고 중복이 없어야 합니다. 그 밖의 항목은 `capabilities.required.iac.send`를 명시한 검증 오류로 거부됩니다. 각 항목은 하나의 `iac.send` scope가 됩니다. kernel은 전달되는 모든 frame을 해당 scope의 capability token으로 중재하므로, Spirit의 bus 전달 내역이 token과 함께 `maosctl audit query --spirit`에 나타납니다. schema v4 이하를 선언한 manifest는 admission 시 이 table이 제거됩니다.

`[capabilities.required.provider]`는 선택 사항입니다. 없으면 Spirit는 provider capability를 갖지 않으며, 있으면 `complete`는 여전히 비어 있지 않아야 합니다.

## Log recall 및 fetch capability

```toml
[capabilities.required.log]
recall = true
fetch = true
```

| Key | 타입 | 기본값 | Scope |
|-----|------|---------|-------|
| `recall` | boolean | `false` | `Scope::LogRecall` |
| `fetch` | boolean | `false` | `Scope::LogFetch` |

두 권한은 독립적이며 table을 생략하면 어느 권한도 부여되지 않습니다. 알 수 없는 key는 거부됩니다. `[capabilities.required.iac]`와 마찬가지로 이 table은 스키마 v5가 필요합니다. 스키마 v4 이하를 선언한 manifest에서는 admission 시 기능 저하 경고와 함께 제거되므로 log scope가 부여되지 않습니다. 이는 스키마 v5에 추가된 선언이며 스키마 버전 상향이 아닙니다.

데몬은 호출마다 별도로 중재하고 capability를 발급하며 감사 기록을 남깁니다. 선언한 capability도 정책, 운영자 거부, 발급 할당량에 따라 거부될 수 있습니다. native와 WASM Spirit은 하나의 kernel 중재 `MediatedLogRecall`을 공유합니다. 로컬 recall은 이번 boot에서 호출자가 보냈거나 기록된 수신자인 공개 가능한 frame을 포함합니다. 수신자는 승인된 incarnation map으로 해석되는 승인된 로컬 수신 주소여야 하며, consent gate가 설치된 경우 이를 통과해야 합니다. 역할만으로는 참여자가 되지 않습니다. 감사 행과 이전 boot는 제외되며 cross-wall recall은 발신자 범위를 유지합니다.

### Capability 발급 할당량 {#capability-issuance-quota}

`DEFAULT_ISSUANCE_QUOTA`는 승인된 scheduler pid마다(하나의 incarnation)
**60 s tumbling window당 60,000회 발급**을 허용하며 monotonic clock을 사용합니다.
용량은 경계를 포함해 정확히 B회이며, 한 window 경계를 가로지르는 burst는
≤ 2·B에 이를 수 있습니다. 중재 순서는 **정책 → context → 할당량 → token**입니다.
정책 및 context 거부는 발급 할당량을 차감하지 않고, 서명 실패는 예약분을
환불하며 실제 발급한 token만 차감합니다. recall의 호출별 폐기를 포함해
발급 후 token 폐기는 발급량을 환불하지 않습니다.

소진 오류는 `CapError::IssuanceQuotaExhausted`이며 governed wrapper에서는
`GovernedMintError::QuotaExhausted`로 변환합니다. spawned-session `iac.send`는
verdict `exhausted`를 기록하고, recall/fetch는 `capability-denied`를 반환하며,
MCP는 `mcp.call.refused:capability-denied` receipt를 기록합니다. CLI-wrapper
spawn은 로컬 및 원격 경로 모두 거부합니다. D1의 계속 진행 방침은 `proc.exec`
grant가 없는 경우에만 유지되며 할당량 소진에는 적용하지 않습니다.

운영자 전용 kind-7 감사 행은 signal/pid/window마다 한 번 발생합니다.
`cap.quota:pressure`는 ⌈80 %⌉, `cap.quota:limit`는 ⌈95 %⌉,
`cap.quota:exhausted`는 첫 거부 시점입니다. kind 7은 Spirit이 절대 회상할 수 없습니다.
전달은 signal/pid/window마다 최대 한 번의 non-blocking enqueue 시도입니다.
기록된 행은 영속적이지만 감사 큐 포화나 writer 종료 시 전달을 보장하지 않습니다.
drop은 `AuditDropSite::Quota`로 집계하고 절대 재시도하지 않습니다.

**한계이며 통제 수단이 아님:** hot swap은 window를 유지하지만 cold swap,
crash restart, unload/재승인 및 새 Worker bind마다 새 용량을 받습니다.
stable-Spirit, principal 전체 또는 Worker spawn churn을 제한하지 않습니다.
다른 governed 호출자는 문자열 오류에 `QuotaExhausted`를 노출하며,
`ShellHost`는 운영자 REPL에서 kernel 오류를 문자열로 표시합니다. 운영자나
manifest가 예산을 설정할 수 없습니다. **Spirit 대상 발급 사전 경고는 없습니다.**
Spirit은 각 경로의 타입화된 거부로 소진을 알게 됩니다. `ScheduleWatchdog`는
발급 전에 rate bucket을 차감합니다. 축소한 token은 실행 시점 권한의 감사 증명이며,
hook ABI에는 token이 전달되지 않습니다.

이는 발급 신호이며, Spirit이 자체 보고한 context token을 manifest
`[budget].context_window_size`와 비교하는 ADR-016의
`ContextPressure`/`ContextLimit`/`EContextExhausted`와 다릅니다.
그 회계는 `18-5-context-token-budget-accounting`이 제공합니다. 선택적 `[budget]`
`context_pressure_threshold` / `context_limit_threshold`((0, 1] 범위, pressure는
limit보다 작아야 함; 기본값 0.80 / 0.95)를 위로 넘을 때마다 커널이
`ContextPressure` / `ContextLimit` 프레임을 한 번 기록하고, 100 %를 넘으면 새 도구
호출이 발급 과금 전에 `CapError::ContextExhausted`로 거부됩니다. 단
`provider.complete`, 메모리 쓰기, `iac.send`(distil 및 hand off)는 거부하지 않습니다.
token 수는 Spirit이 자체 보고하며 커널은 추정하지 않습니다.

### Recall 동의 및 프로덕션 한계

발신자가 아닌 수신자에게는 만료되었거나 grant 범위 rupture가 발생했거나 `Withheld`인 envelope가 적용되어 frame이 recall에서 제외되고 fetch는 `consent-withheld`와 `log.fetch.refused:consent-withheld` receipt를 남깁니다. `HeaderOnly`는 `payload-available = false`인 메타데이터를 나열하고 fetch는 마찬가지로 거부합니다. `ConsentEnvelope.recall`은 데몬 측 정책이며 기본값은 `Full`, 알 수 없는 값은 `Withheld`입니다. WIT에는 포함되지 않으므로 guest는 효과만 볼 수 있습니다. lossless frame 계약의 이 예외는 `17-8-consent-recall-policy`로 비준되었습니다.

**프로덕션 한계(AC3.6 / rule 11):** HEAD 기준으로 `HeaderOnly`/`Withheld`를 설정하는 프로덕션 granter가 없고, 프로덕션에 `ConsentGate`가 설치되지 않으며, envelope가 있는 frame은 A2A delegation intake를 통해서만 승인된 로컬 수신자에게 도달합니다. peer-identity rupture에는 envelope가 없으므로 아무것도 보류하지 않습니다. native compiled-in Spirit의 bus 전송은 pid 0으로 기록됩니다(비목표). WIT import, 오류, 동의 세부 사항, `handle-frame` 안에서만 사용할 수 있다는 제약은 [WASM Component Spirit](/cookbook/wasm-component-spirit)을 참조하세요.

## Admission 경계

WASM-component Spirit는 sandbox tier `T2`를 선언합니다. 기본 MAOS binary는 전체 manifest를 검증한 뒤 Export Hold 2가 `wasm-host` feature를 비활성화하는 동안 `wasm_engine_off`로 component를 거부합니다. `wasm-host` build는 `maos run`을 통해 격리된 T2 runner에서 component를 실행하며, runner가 제공하지 않는 in-process 기능(operator door, topology, hot-swap 후속 Spirit)은 `spawned_surface_unsupported`로 거부됩니다.

## `[cli_wrapper]` — Worker manifest {#cli-wrapper-worker-manifests}

Worker manifest는 `[class]` 대신 하나의 `[cli_wrapper]` table을 사용합니다. 둘 다 선언하면 manifest gate 3에서 `manifest_schema_conflict`로 거부됩니다. `[cli_wrapper]` manifest에는 `manifest_schema_version`이 없습니다(해당 스키마 버전은 Story 20-5가 담당합니다). `[cli_wrapper]`와 `[cli_wrapper.posture]`의 알 수 없는 key는 거부됩니다.

| Key | 타입 | 필수 / 기본값 | 허용 값 또는 제약 |
|-----|------|----------------|-------------------|
| `command` | `string` | 필수 | 비어 있지 않아야 합니다. |
| `argv_prefix` | `string[]` | 선택; 기본값 `[]` | — |
| `output_shape_version` | `string` | 필수 | 예: `"1.0.0"`. |
| `skill_bundle` | `string[]` | 선택; 기본값 `[]` | — |
| `recovery_policy` | `string` | 선택; 기본값 `respawn_with_context` | `respawn_with_context`, `respawn_fresh`, `escalate`; 기본값은 load 시 거부됩니다. |
| `egress` | `string[]` | 선택; 기본값 `[]` (egress 없음) | 항목 형식은 `host:port`; 중복은 거부됩니다. |
| `[cli_wrapper.posture].stdio_shape` | `string` | 필수 | `ndjson_over_stdio`, `json_rpc_over_stdio`, `raw`. |
| `[cli_wrapper.posture].control_channel` | `string` | 필수 | `signals`, `named_pipe`, `stdin_commands`. |
| `[cli_wrapper.posture].shutdown_signal` | `string` | 선택 | `SIGTERM`, `SIGINT`, `SIGKILL`, `SIGHUP`, `SIGQUIT`, `SIGUSR1`, `SIGUSR2`. |

Egress host는 소문자 DNS label 또는 IPv4 literal이며, port는 `1`–`65535`입니다. manifest egress는 operator의 host-grant destination 집합의 부분집합이어야 합니다. grant의 host만 지정하면 `:443`을 의미합니다. Upstream traffic은 `HTTPS`를 사용하며, 명시적으로 허가된 IPv4 loopback literal에만 plain `HTTP`가 허용됩니다.

Admission을 위해 `[sandbox] tier`가 `T3`로 해석되어야 합니다. `T0`–`T4`만 parse되며 `hardened` tier는 없습니다. operator 소유의 `MAOS_HOST_GRANTS`에 일치하는 grant가 필요합니다. 기본 `respawn_with_context` policy는 load 시 거부됩니다. `T3`에서는 `control_channel = "signals"`인 `ndjson_over_stdio` 또는 `raw`만 허용되며, stdin을 유지하는 posture는 거부됩니다. 지원되는 command는 `codex`, `claude`, `worker-cli-fixture`, `worker-probe-fixture`입니다.
Worker 리소스 제한은 선택적이며 서로 독립적입니다. `cpu_max_pct`는 CPU 한 개 대비 양의 백분율(`10` = `--cpus=0.10`), `memory_max_mb`는 MiB, `pids_max`는 양의 `u32` 프로세스/태스크 상한, `fd_max`는 별도의 파일 디스크립터 상한입니다. 각 값은 manifest와 operator 중 더 엄격한 제한으로 결정됩니다. 생략 시 `None`이며, 허용되는 schema v4/v5 manifest에서도 동일합니다. Native Linux T2에서 명시적 CPU/PID 제한에는 쓰기 가능한 위임 cgroup v2가 필요합니다. memory-only 요청은 적용되는 `RLIMIT_AS` 및 선택적 `RLIMIT_NOFILE`로 대체될 수 있으며, 성공한 각 fallback launch마다 `ResourceCeilingDowngraded=20` 정보 행 하나가 영속 기록됩니다. `pids_max`는 Linux에서만 적용되며, native macOS 및 Windows sandbox는 이를 적용하지도 거부하지도 않습니다. T3 runtime 기본값과 native 제약은 [CLI wrapper Spirit cookbook](/cookbook/cli-wrapper-spirit)을 참조하세요.

Runtime profile과 operator prerequisite는 [CLI wrapper Spirit cookbook](/cookbook/cli-wrapper-spirit)을 참조하세요.

```toml
# A Worker manifest: [cli_wrapper] replaces [class]; never declare both.
[cli_wrapper]
command = "codex"
argv_prefix = ["exec", "--json", "--sandbox", "workspace-write"]
output_shape_version = "1.0.0"
recovery_policy = "escalate"
egress = ["api.openai.com:443"]

[cli_wrapper.posture]
stdio_shape = "ndjson_over_stdio"
control_channel = "signals"
shutdown_signal = "SIGTERM"

[sandbox]
tier = "T3"

[author]
name = "OpenAI"

[on_crash]
action = "nack"
```
schema v4 manifest는 N-1 window에서 계속 허용됩니다. v4 manifest는 `wasm-component`를 선언할 수 없습니다.
