## LOCKED Design Decision — manifest stays fail-closed; NO forward-compat warn-and-ignore window

**DECIDED by Lunarpulse 2026-05-31. This is binding for the dev — do NOT reopen it; implement exactly as specified below.**

The epic AC (line 198) reads *"unrecognized fields are warned, not rejected."* On analysis this clause is in tension with the kernel's fail-closed security model, and the tension is resolved in favor of **fail-closed**. Reasoning the dev must internalize:

- **The manifest is a SECURITY artifact** (sandbox tier, capability scopes, posture, provider pinning). Silently warning-and-ignoring an unknown field in it is a **fail-OPEN** behavior: an older kernel could admit a Spirit while ignoring a newer field that was meant to *constrain* it (e.g. a future `required_capabilities_v2` or a tighter sandbox directive). That directly contradicts the substrate's fail-closed invariants (T1-reject, no-half-admitted-state, `deny_unknown_fields` everywhere, §8.5 ABI break rule). The architecture documents NO manifest warn-not-reject path (confirmed by exhaustive search).
- **The AC block is scoped to the BACKWARD direction** ("kernel version V loads a manifest written for V-1"). In that direction there are NO unknown fields — V-1 has FEWER fields, all known to V. The real N-1 degradation is *missing newer sections*, defaulted via `#[serde(default)]` — and THAT is what gets the WARN-level `tracing` notes. Unknown fields only arise in the FORWARD direction, which NFR-Maint-9 does not cover.

**The locked behavior — the `manifest_schema_version` gate is fail-closed in BOTH directions, with typed errors at admit:**

| Declared `manifest_schema_version` | Behavior | Typed error |
|---|---|---|
| `== CURRENT` (2) | strict load, `deny_unknown_fields` (unchanged) | — |
| `== N-1` (= `MIN_SUPPORTED`, 1) | **loads**; emit `tracing::warn!` degradation note per newer section absent in the V-1 manifest (defaulted via `#[serde(default)]`) | — |
| `< MIN_SUPPORTED` (N-2, e.g. 0) | hard-refuse at admit | `SecurityError::EAbiTooOld { declared_schema, min_supported }` |
| `> MAX_SUPPORTED` (future/N+1) | hard-refuse at admit — **NOT warned-and-loaded** | `SecurityError::EAbiTooNew { declared_schema, max_supported }` |
| any unknown field within an in-window schema | hard-reject (a field unknown to a *known* schema is a malformed manifest, not forward-compat) | `ManifestError::Toml(...)` (unchanged, fail-closed) |

So: **keep `#[serde(deny_unknown_fields)]` everywhere; do NOT add a `#[serde(flatten)]` capture, a `toml::Value` pre-parse diff, or any N+1 lenient deserialize path.** The forward case is handled by refusing the whole manifest with the typed `EAbiTooNew` (the symmetric sibling of `EAbiTooOld`) — promoting the existing stringly above-window rejection (`manifest.rs:262-272`) to a typed error at admit, exactly as the below-window case is promoted to `EAbiTooOld`. A future Spirit gets a clear "this Spirit needs a newer kernel" message, not a cryptic serde failure and not a silent fail-open admit.

### Architecture compliance (binding rules — cite in PRs)
- **ABI Stability Triple** = `(kernel_version, abi_version, manifest_schema_version)` — a TRIPLE, not a pair. `abi_version` governs the `Spirit`/`KernelHandle` vtable + capability-ID space (SemVer; major break = vtable/semantics change; frozen at `1` since 1b.4). `manifest_schema_version` governs the TOML surface INDEPENDENTLY. `kernel_version` is product-facing and includes both as a compatibility set.
