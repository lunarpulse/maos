### Kind-28 fixed-field exemptions: what is actually established

The real AuthorizationRecord makes `event`, `trusted_intent` and `trusted_origin` static strings; ScopeDecision makes `kernel_verdict` static; Claims::Truncated computes `sha256` from frame bytes (`spirit_session.rs:704–737,951–988`). Those actual receipt fields are not user-supplied Alice strings. A hypothetical nested arbitrary object under one of these keys is not a demonstrated typed session-emission path and is not reported as a new exploit.

However, **the exemption is not structurally justified for every field it covers**. `SchemaLifecyclePayload.schema_content_hash` and `.supersedes` are unconstrained Strings. The real operator door accepts string `content_hash` and `supersedes` without digest validation (`operator_door.rs:2338–2378`); `register_schema_lifecycle` checks only nonempty ratified_by before persisting them (`transparency_log.rs:3074–3091`). Thus an accepted lifecycle record can carry `alice` in either exempt value, and selection/scrubbing/certification will all ignore it. The fixture even uses non-SHA256 deadbeef/cafe values, so it does not establish a validated-hash invariant.

This retention already existed under the parent kind-28 path-only implementation, so it is **not a third newly introduced finding**. It does prevent claiming complete value erasure merely from a key spelling. For complete closure: enforce canonical digest forms on the real ingress and apply path/subtype plus value validation to exemptions; handle already persisted noncanonical personal values instead of automatically exempting them. Required witness: exercise the real admission route with noncanonical principal-bearing content_hash/supersedes, require rejection before persistence or subsequent erasure, and preserve canonical hash controls. The independent schema registry itself is outside this patch; do not imply this TL review proves its erasure.

### JSON escapes and late-window certification: one helper is not one predicate

The helper correctly decodes JSON escapes **once a row reaches it**, and replacement operates on decoded string values. But the complete discovery path still contains `instr(payload_redacted, CAST(?1 AS BLOB)) > 0` (`transparency_log.rs:2001`) before calling that helper. An escaped goal with `\u0061lice` but no literal Alice bytes is excluded. More directly, an ordinary valid principal containing a quote, such as `ali"ce`, is JSON-serialized with an inserted backslash, so its raw principal bytes need not occur anywhere in the stored body.

The late certifier has no equivalent raw prefilter. A single late receipt whose only nexus is an escaped goal is decoded and recognized by certification; the next sweep excludes it through instr, advances state.through past it, and the following certifier no longer examines that row. It can therefore certify while the value remains. The finite row-window advancement is at `erasure_sweep.rs:127–141,265–267`; its final tail check is at `:303–376`. This is not an infinite-retry claim.

The raw SQL exclusion predates this commit and already broke equivalent escaped cases, so it is **not included in the new-finding count**. Nevertheless, correction-round2.md:17 saying discovery/replacement/certification cannot diverge is false for the complete pipeline. Required closure fix/witness: let kinds 28/29 reach decoded value selection even when their raw bytes do not contain the subject; test escaped quote/backslash principals and Unicode escape spellings in both the initial snapshot and the existing one-shot late hook, checking the final decoded payload and cited-distillate closure. Retain raw matching for other kinds and bounded scan behavior. The two added late tests contain only literal Alice bytes and do not establish this case.
