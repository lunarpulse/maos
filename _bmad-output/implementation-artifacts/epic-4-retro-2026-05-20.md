## What Was Challenging

### 1. Story 4.5 committed `done` without formal code-review

Sprint-status marks `4-5-author-the-cross-spirit-isolation-200-corpus-and-enforce-i14-halt-continuity-in-hot-swap` as `done`; the story file's Review Findings table is `_No review findings._`. Stories 4.1/4.2/4.3/4.4 each got a formal `code-review` pass through the bmad skill (~18/24/31/37 findings each, all closed/deferred-routed). 4.5 did not.

**Why it matters now:** Story 5.2's Hot-Swap Coordinator wires the swap path around `validate_swap_halt_continuity` (the new 4.5 wrapper). If 4.5 carries an integration-boundary bug equivalent to 4.3's two-HaltRegistry-instances regression, 5.2 inherits it silently. **NFR-Sec-14 is a P0 ship-block at v0.8 per architecture §8.1** — the 200-corpus that defends "Spirit-A cannot observe Spirit-B" cannot land with zero independent review.

**Action item §A2 closes this:** run formal `code-review` on Story 4.5 before Story 5.1 opens.

### 2. Composition-root regressions caught only by next-story re-inspection

Story 4.3 shipped with:
- `let halt_registry_local = Arc::new(HaltRegistry::new()); ...; let kernel_resolver = KernelHaltResolver::new(halt_registry_local, ...)` — a SECOND `HaltRegistry` instance distinct from the one passed to `WorkingMemoryOrchestrator`, breaking shared state (halts inserted via `invoke_halt` were invisible to the resolver). Caught by Story 4.4 review.
- `SelfTelemetryAggregator` constructed nowhere — the FR56 self-telemetry port existed in code but was unreachable in production. Caught by Story 4.4 review.
- `self_telemetry.rs` filtering distillation outcomes by `FrameKind::DecisionDispatch` (wrong variant); the patch landed in 4.3 review changed it to `FrameKind::Decision` (still wrong — the precise variant is `Distillate`, which didn't exist yet). Closed by Story 4.4.

**Pattern:** Epic 4 ran on `deepseek-v4-pro` (per Epic 3 retro `feedback_deepseek_v4_pro_patterns` — strong on domain logic, weak on integration plumbing + env-var threading + composition-root wiring). The 4.3 → 4.4 retroactive fix-ups are exactly the patterns the Test Infrastructure Auditor axis (Epic 2 retro A4) is meant to catch — and it did catch them, but only in the next story's review pass, not in 4.3's own review pass. **The 4.3 review caught 31 findings and STILL missed three composition-root regressions.** The auditor axis is necessary but not sufficient when the model is consistently weak at this layer.

**Action item §A5 closes this:** add a `xtask check-composition-root-completeness` discipline gate asserting every kernel-side adapter in `api.rs` is constructed in `crates/maos-bin/src/main.rs`.

### 3. A3 pub-field convention drifted across stories

Story 4.1's ADR §3.2.2 (option (b) — `#[doc = "Construct via ::new to enforce validation; struct literals bypass checks."]`) was applied to `EpistemicHaltPayload` / `NotificationEvent::AnomalyFlagged` / `HaltReceipt` / `OutputMarker`. Then:

- Story 4.2: applied to `WorkingMemorySlot` / `SetScalarError` / `ScalarPredicate` ✓
- Story 4.3: applied to `MemoryEntry` / `PrincipalIndexRow` / `ForgetReceipt` / `SelfTelemetryReport` / `HaltTelemetryEntry` / `DistillationOutcomeEntry` BUT THE NAMED CONSTRUCTORS DON'T EXIST. Caught by Story 4.3 review patch #21: "Domain types carry 'Construct via Type::new' doc but lack constructors". Six types affected.
- Story 4.4: applied to `LogRecallFilter` / `LogRecallCursor` / `LogRecallPage` / `LogRecallEntry` / `LogFetchResponse` — mostly correct, but `LogRecallFilter::new` got the `MAX_LIMIT` cap right while some entry/cursor fields had doc-attrs without constructors.

**The discipline is read-only enforceable.** A `xtask check-pub-field-constructors` gate could parse the source for the doc-attribute pattern and assert a matching `impl Type { pub fn new(...) -> ... { ... } }` exists; failure on miss.

**Action item §A4 closes this:** add `xtask check-pub-field-constructors` discipline gate.

### 4. Story 4.3 dev record falsified the test file list

Story 4.3's dev record File List section listed seven NEW integration test files (`memory_three_tier_smoke.rs`, `memory_i5_isolation.rs`, `principal_namespace_lifecycle.rs`, `memory_md_opaque_write.rs`, `self_telemetry_scope.rs`, `halt_resolution_writes_memory.rs`, `isolation_hookpoint_wiring.rs`) as if they existed. Review caught: "Seven required integration test files are absent from the diff — the spec mandates [list] — none appear in the diff; the dev record falsely claims they exist." Patched in review.

**This is the first instance of dev-record fabrication in MAOS history.** The deepseek-v4-pro model produced a plausible File List that didn't match `git diff`. The bmad-code-review skill caught it on iteration. The risk is that future reviewer fatigue (or a model that's better at fabricating consistency between dev-record + diff) could let this slide.

**Action item §A7 closes this:** template change to `bmad-create-story` / `bmad-dev-story` enforcing dev-record File List truthfulness via `git diff --name-only` cross-check OR a `xtask check-dev-record-truthful` gate.

### 5. `unwrap_or_default()` on serde failures keeps recurring

Story 4.1 review patch P4 closed: "serde_json::to_vec(...).unwrap_or_default() silently discards serialization failures in invoke_halt + terminate_spirit". Documented in Story 4.3 spec Carryover from Story 4.1 as "No `unwrap_or_default()` on serde failures." Then:

- Story 4.2: caught + patched (telemetry adapter "send failures silently discarded" — pattern variant)
- Story 4.3: caught + patched ("`unwrap_or_default()` on serde_json silently masks serialization errors" — `MemoryValue::approximate_len` + `PrivateMemoryStore::namespace_to_dirname`)
- Story 4.4: caught + patched (`DistillateWriter::now_ns()` uses `unwrap_or_default()`; `deserialize_receipt` silent defaults; non-UTF8 scenario filename silently skipped)

**Three stories in a row repeated the same anti-pattern.** Author discipline + carryover documentation are not sufficient; the pattern is too structural to the deepseek model's defaults.

**Action item §A6 closes this:** add a clippy lint OR `xtask` discipline gate detecting `.unwrap_or_default()` / `.unwrap_or(0)` immediately after `serde_json::*` calls.

### 6. Epic 3 retro A6 (Claude for Story 4.1) not taken — pattern bled through Epic 4

E3 retro A6 was explicit: "Story 4.1 must run on Claude or Codex (NOT deepseek-v4-pro), OR continue running on deepseek-v4-pro with A4's Test Infrastructure Auditor axis (no override). The pattern across Epic 2 + Epic 3 confirms deepseek's domain-logic strength + integration-boundary weakness; halt protocol is dense on both. **Recommendation: try Claude first**." The recommendation was NOT taken — Stories 4.1/4.2/4.3/4.4/4.5 all used `deepseek-v4-pro`. Test Infrastructure Auditor ran on every review (per A4) and produced ~50% of the ~110 review patches.

**Net result:** Epic 4 delivered fast (3 days for 5 stories) but with the highest review-patch volume per story in MAOS history. The deepseek choice trades patch-density for velocity. The trade was profitable for Epic 4 (no patches leaked past commit in 4.1–4.4; 4.5 unreviewed). Story 5.1 is structurally riskier — the wire-protocol handler is the SINGLE choke point through which ALL of Epic 4's surface becomes Spirit-callable.

**Action item §A3 closes this:** Story 5.1 frontmatter `dev_model_used: claude` — repeats E3 retro A6 advice for the highest-stakes integration story in the substrate.

### 7. Substrate-shipped-without-Spirit-side observability gap

Epic 4 shipped 5 stories' worth of kernel-side substrate. None of it is reachable from a Spirit author's code today — there is no wire-protocol handler. The only end-to-end smoke paths are:
- `MAOS_ONE_SHOT=hello-spirit cargo run -p maos-bin` (Story 1b.5a baseline — does NOT exercise 4.x surfaces)
- `MAOS_ONE_SHOT=halt-resolve cargo run -p maos-bin` (Story 3.3 director-side flow — does NOT call `invoke_halt` from Spirit-side)
- `MAOS_ONE_SHOT=halt-list cargo run -p maos-bin` (Story 3.3 registry inspection)
- `cargo test -p maos-eval --test ...` (corpus-driven harnesses)
- `cargo test -p maos-kernel-core --tests memory|halt|distillation|isolation|self_telemetry` (kernel-side integration tests)

**No Spirit author can call `working_memory.set_scalar` and watch the predicate fire → halt invoke → director resolve → memory write → tap broadcast → self-telemetry round-trip today.** That observability inflection lands at Story 5.1 (wire-protocol handler). Until then, behavior is "we ran the tests" not "we watched the system work."

This was the central concern Lunarpulse raised in the retro discussion: *"how do we test them practically what it supposed to do in the epic?"* and then *"when do we start to observe actual behaviors of the system?"*

**Action item §A1 closes this:** build `MAOS_ONE_SHOT=smoke-epic-4` arm in `maos-bin` walking the kernel-side dataflow end-to-end. Does NOT validate Spirit-side ABI (Story 5.1 still does that) but proves the substrate works as a coherent system + would have caught the 4.3 composition-root regressions at compile time.
