## Findings

**F1 — P3 (hardening): the "one production adapter on the selected provider" property is not machine-checked; `SecurityManagerAdapter` is exempt from the gate's duplicate-construction assertion.**
`xtask/composition-root-whitelist.toml` (top block, `"SecurityManagerAdapter"` entry) exempts the adapter from the exactly-one-construction check of `check-composition-root-completeness.rs:98-107`, and the new naming ban only refuses the *name* `RingCryptoProvider` — not a second adapter built from a *different* provider instance (e.g. a future daemon arm calling `crypto_provider::select` again with another home, or passing any non-ring `Arc<dyn CryptoProvider>`). Today there is exactly one production construction (`main.rs:2257`) plus the annotated smoke arm (`:15699`, `p1-allow` marker at `:15698`); `check-service-boundary` P1 would force an explicit allow-marker on a second owner, so a *silent* addition is unlikely — but an explicitly-annotated second root with a divergent provider would pass all gates green. **Exploit at this commit: none (requires future code).** **Fix sketch:** extend the gate to assert exactly one `SecurityManagerAdapter::new` in `main.rs` outside `#[cfg(test)]` mods and outside `smoke_*` demo arms whose second argument is spelled `Arc::clone(&crypto)`/`crypto` from the root binding (or re-ask the rejected KI `identity()` row, `D-20-13-03 B`, as a v1.5 identity check). **Witness need:** plant a second production construction fed by a second `select()`; the gate must go red.

**F2 — P3 (hardening): the naming-ban scan's coverage is narrower than the invariant it enforces.**
`crypto_provider_violations` (`check_composition_root_completeness.rs:147-170`) only scans files whose path contains `/src/` under `crates/`, `spirits/`, `examples/`, `xtask/src` — so `crates/*/build.rs`, repo-root `tools/`, `templates/`, and root `tests/` are invisible to it — and it bans the *name* `RingCryptoProvider` only, so a production `impl CryptoProvider` that always accepts, living in a lib crate under `/src/`, would not be refused by anything (today none exists; verified). Also note a plain `pub use …RingCryptoProvider;` re-export (e.g. `security/mod.rs:21`) is not itself flagged (only renames/use-sites are) — benign while use sites are caught, but worth stating. **Exploit at this commit: none.** **Fix sketch:** add `crates/*/build.rs` and `templates/` to the walk, and add a leg refusing any non-`#[cfg(test)]` `impl CryptoProvider` block outside the allowlisted provider files. **Witness need:** plant an always-accepts impl in a lib crate's production code and a ring naming in `templates/`; both must red.
