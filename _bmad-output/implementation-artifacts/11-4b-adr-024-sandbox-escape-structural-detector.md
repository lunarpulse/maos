## Story

**As** the operator (and the watching Spirit) of a security-bound MAOS deployment (NFR-Sec-3; Journey: Reza Cortex / adversarial-host posture),
**I want** a **structural** sandbox-escape anomaly detector that lives **outside** the kernel — a read-only Transparency-Log consumer that correlates the kernel's raw structural facts (a real seccomp/Job-Object sandbox kill → a `SandboxBlock` TL row) against the Spirit's manifest declaration and raises an **anomaly signal with a structural rationale** — with the kernel wired to actually **emit** that raw fact on a real sandbox kill (the survey found the producer dead), the detector proven on a **live-syscall proven-red (no mock)** to meet a **TP-floor + FP-ceiling**, and the boundary that **the kernel raises a structural alarm and never classifies intent** mechanically enforced,
**So that** MAOS satisfies the v2.0 NFR-Sec-3 sandbox-escape-detection commitment **without growing the kernel's responsibilities** — the kernel stays the small, dumb mediator that "learns no patterns" (ADR-006): it records *what the OS enforcement layer observed*, and the operator/Spirit judges *what it means* (ADR-024 §2, the STRUCTURAL-NOT-SEMANTIC clarification) — and **without breaking the v1.0-frozen ABI or drawing the kernel-core budget beyond the bounded producer-wiring** (ADR-024 §4; ADR-038 ≤6 KLOC ceiling).

### Explicitly NOT in 11.4b (defend at review)
- **An in-kernel pattern matcher / escape classifier.** ADR-024 §5 REJECTED it (violates ADR-006 §I9, grows the ceiling, makes the malice judgment a kernel concern). All correlation/interpretation is **user-space** in `maos-escape-detector`. The kernel stores no escape patterns, no per-Spirit "what an escape looks like" history.
- **A `malice` / `verdict` / `severity` / `intent` field on the kernel emission.** ADR-024 §5 + the Gate FORBID adding one. `CapAuditEvent::SandboxBlock` carries `{spirit_pid, attempted_syscall, sandbox_tier}` and nothing more — AC2 asserts the *absence* is preserved. Adding one "to help the detector" is RED.
- **A kernel-resident broadcast / push-stream for sandbox events** (a `scalar.tap`-style `broadcast::Receiver`). ADR-024 §3 REJECTED it *for the initial form* — no measured detection-latency requirement justifies the new kernel surface; the query/tail path over the existing TL sink-of-record meets the structural-detection need. It is retained as a **future, bounded** option under a measured revisit (F7) — **out of scope here.**
- **Any `maos-kernel-core` dependency in the detector.** ADR-024 Gate (out-of-kernel invariant) + the Story-1a.4 decoupling rule. The detector is the `maos-audit` shape: read-only TL, kernel-core dev-dep only (if at all). Enforced by `check-service-boundary` / `check-dependency-closure`.
- **Putting the detector on any hot path.** It is an offline/tailing consumer of a write-then-query store. No IAC/token-path coupling (unlike a PDP — this is not authorization; L10).
- **fd-table-growth + unexpected-outbound-IAC runtime signals — DEFERRED (F2 RESOLVED).** v2.0 delivers **signal 1 only** (seccomp exit-classification vs manifest). fd-growth + outbound-IAC → a bounded follow-up (each needs new runtime infra — `/proc/<pid>/fd` sampling / conntrack — with no live proven-red substrate today). NFR-Sec-3 is annotated "1 of 3 @v2.0", **not** marked satisfied (the honesty clause; do NOT claim NFR-Sec-3 done).
- **Wiring production sandboxing (making `spawn_and_bridge` Spirits actually seccomp-enforced) — OUT OF SCOPE (CATCH-0).** The production CLI-wrapper path (`spawn_and_bridge`, `runtime.rs:449`) spawns a plain UNSANDBOXED `Command`; `spawn_sandboxed` has zero production callers. 11.4b wires the emit onto the launcher/backstop that **already** applies T2 (the 11.1a WASM seam) and **names this gap out-of-scope in ink** — it is a separate security-hardening story. 11.4b **never** absorbs it, and **never** proves AC3's red against a test-only spawn.

### The detection seam — what 11.4b builds, grounded in the live tree (survey 2026-07-05)
The full pipe **exists and is half-wired**: `SandboxViolation` (`security/sandbox/mod.rs:73-78`) → `CapAuditEvent::SandboxBlock` (`maos-capability/src/cap_audit/mod.rs:99-104`) → `CapAuditWriter` match arm writes `FrameKind::SandboxBlock=8` with `FrameOrigin::Kernel` (`capability/cap_audit/writer_task.rs:107-122`) → TL (`transparency_log.rs:66`, discriminator `=8`) → `maos-audit` read-side maps it back (`kind_from_string`, `maos-audit/src/lib.rs:696`). The **writer half is live in production** (channel `main.rs:1639`, writer spawned `main.rs:2198-2201`). **The producer half is dead:** `classify_exit` (`security/sandbox/mod.rs:164-198`), `emit_sandbox_block` (`security/mod.rs:469-486`), and `emit_t3_escape_block` (`cap_audit_bridge.rs:14-28`) have **zero call sites**; only the stderr-only `emit_t3_escape_block_probe` runs, once, in `smoke-t3-sandbox-5` (`main.rs:5426`) — a smoke print, not production detection. **11.4b closes exactly this gap** (wire `classify_exit`+`emit_sandbox_block` on the real reap) and builds the out-of-kernel consumer (`maos-escape-detector`) that reads the resulting real rows.

### The read-only-TL-consumer template — copy `maos-audit` verbatim as the skeleton
`crates/maos-audit/src/lib.rs` is the canonical read-only TL consumer: opens the TL SQLite with `OpenFlags::SQLITE_OPEN_READ_ONLY | SQLITE_OPEN_NO_MUTEX` (`:185-187,357-359,529-531,1110-1112`), library dependency graph is **kernel-core-free** (`maos-kernel-core` is a **dev-dependency only**; runtime deps `rusqlite`, `serde`, `serde_json`, `thiserror`, `maos-domain`, `ed25519-dalek`, `sha2`, `hex`, `hkdf`), and `kind_from_string` already maps `"sandbox.block" | "SandboxBlock" => Some(8)` (`:696`). `maos-escape-detector` is the **same shape of consumer** — the only new thing is the correlation logic (kind=8 frame + manifest → anomaly) and the anomaly-signal output. **This is why the detector is ZERO-kernel** (ADR-024 Consequences).

### The producer-wiring — ZERO kernel-core, edge-wired (RESOLVED CATCH-0/F1)
`classify_exit(status: ExitStatus) -> Option<SandboxViolation>` (`security/sandbox/mod.rs:165`) is a pure post-mortem classifier: `#[cfg(unix)]` `SIGSYS → {attempted_syscall:"unknown", sandbox_tier:T2}` (`:170-175`), `SIGKILL → {"possible-oom-or-resource-cap", T2}` (`:176-181`), `#[cfg(windows)]` `0xC0000005 → {"access-violation-possible-sandbox", T2}` (`:188-195`), else `None`. **Every arm hardcodes T2 and cannot name the syscall (L5).** `emit_sandbox_block(&self, sender:&cap_audit::Sender, spirit_pid:u32, attempted_syscall:&str, sandbox_tier:SandboxTier)` (`security/mod.rs:469-486`) builds the `CapAuditEvent::SandboxBlock` and `sender.try_send`s it (non-blocking — ADR-030). **CATCH-0 (the correction):** the story's original wiring target `cli_wrapper/runtime.rs:635` is **RETIRED** — that reap is `spawn_and_bridge` (`runtime.rs:449`), a plain **UNSANDBOXED** `Command::new().spawn()`; `spawn_sandboxed`/`classify_exit` have **zero production callers**. So the wiring goes at **the launcher/composition-root that owns the real sandboxed reap** (the 11.1a T2 subprocess-launch seam Task-0 pins) — the edge calls the *existing* kernel-core `classify_exit`+`emit_sandbox_block` → **ZERO kernel-core delta** (`check-kernel-baseline` stays @ 23081). **Do NOT** wire the smoke path (`main.rs:5426`) or `emit_t3_escape_block` (a distinct T3-container path). **Contingency:** if Task-0 proves the sole real sandboxed reap is unavoidably inside kernel-core, pin the bounded re-pin from 23081, HISTORY-disclosed naming the surface (mirror the 11.4a `+17`/`+41` entries at `kernel-core-baseline.toml:185-204`) — otherwise ZERO holds. **Scope line:** proven-red on the real launcher reap OR name the CLI-wrapper-unsandboxed gap out-of-scope (a separate hardening story) — never a test-only spawn.

### The no-verdict invariant (AC2) — assert the ABSENCE, do not add a field

The producer-wiring emits the *existing* fact — it adds no field. All rationale lives in the **detector's** anomaly output.
