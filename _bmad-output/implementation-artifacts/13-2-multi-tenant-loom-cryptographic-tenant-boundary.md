## What this story is, in one paragraph

13.1 built the **physical** wall: each team's rows live in a Postgres database another team's connection cannot name, guarded by a store-internal `team_guard` that does a **presence-only string-equality** check (`caller_team == home_team`). 13.1 explicitly did **not** close the same-region insider-forgery threat (ADR-055 §4 / threat-model T1: *"A same-region insider able to forge a team stamp remains live until Story 13.2"*). 13.2 is the **cryptographic** wall (Fork-4, ADV-055-1): a **second HKDF stage** welds a per-team Ed25519 signing key over the region seed; `source_team` enters the canonical KV leaf pre-image under a **v2 domain tag** (v1 leaves byte-identical); and a cross-team bundle is **verified under the key derived from its *claimed* `(region, team)`** — so a same-region insider forging a bundle stamped as another team is **refused at `verify`, never lands** (the forgery is closed at the strongest point: entry). **This is Option A, ratified in Round 2** after scouts proved the read path has nothing to verify (`collective_memory` persists no signature column; the replication crypto path has zero production callers): `team_guard`'s read stays presence-only (13.1), and the read-time D1 residual + per-row attestation persistence + production wiring defer to 13.3, where cross-team rows first exist. Like 13.1, this is a **MECHANISM story** proven at the verify seam — it builds no production cross-team writes (13.3), multi-store routing (13.5c), or audited refusal (13.5c).

## Story

As a **MAOS operator running Reza's 400-person fintech as one governed Cortex (three teams: security, support, data — normally sharing a region)**,
I want **each team's Loom-lite rows welded to a per-team Ed25519 key derived by a second HKDF stage over the region seed, `source_team` bound into the canonical Merkle leaf under a versioned v2 domain tag (v1 rows byte-identical), and a cross-team bundle admitted only when it verifies under the team key derived from its *claimed* `(region, team)` — never from a label the bundle carries**,
so that **a member of team B in the same region can no longer land a row that appears to belong to team A: the forged bundle is refused at entry, the tenant boundary is cryptographic and not just physical, and the same-region insider-forgery threat that ADR-055 §4 and threat-model T1 carried as LIVE-until-13.2 is closed by construction, not by operator honesty.**

## Design forks for preflight (grounded recommendations — G-numbered like 13.1's F-series)

Fork-4 itself is **ratified** (§15.11:167 — per-team HKDF weld, `verify_bundle` derives pubkey from `(claimed_region, claimed_team)`, `source_team` in `canonical_kv_leaf` v2, `team_guard` → signature verification). These are the **implementation-shape** decisions the ratified fork leaves open. Each is grounded against code; each has a recommendation the ACs assume.

- **G1 — where the team weld lives.** The region weld (`derive_region_signing_seed`/`derive_region_pubkey`) is in `crates/maos-audit/src/sealed_export.rs:26,40`; `bundle.rs:29` imports it. **Recommend: add `derive_team_signing_seed`/`derive_team_pubkey` next to the region ones in `maos-audit::sealed_export`** — the second stage literally welds over `derive_region_signing_seed`'s output, symmetry keeps one crypto home, and `bundle.rs` already imports from there. *Trade-off to verify at preflight:* this grows `maos-audit`'s public API surface — confirm no `cargo-public-api`/ABI gate reds on `maos-audit` (there is none for the 9.4b additions, but check). The alternative (a new `maos-loom-lite` crypto module) avoids any audit-surface question at the cost of re-stating the HKDF idiom. Both are **ZERO kernel-core Δ** (neither crate is `maos-kernel-core`).
- **G2 — leaf v2 byte-compat trigger.** `canonical_kv_leaf` v2 adds `source_team` to the pre-image, but *when* is a leaf v2 vs v1? **Recommend: `source_team: Option<TeamId>`; `None` → emit the exact v1 domain tag + v1 layout (byte-identical, 11.2a untouched); `Some` → v2 tag + v1 layout + appended `source_team`.** At 13.2, first-party local writes leave `source_team` **NULL** (stay v1) — only re-attested cross-team copies (built by 13.3, or synthesized in 13.2 tests) set it. **Reject** populating `source_team = home_team` for every local row: that re-roots every team's store the moment 13.2 lands and breaks 11.2a's *"v1 leaves untouched — byte-compat by construction"* (§15.3:57) for all new rows. The additive nullable column is the 9.2b idiom; the versioned tag namespaces v1 from v2.
- **G3 — the read-path guard mechanism. SUPERSEDED by Round 2 → Option A (see the Round-2 record below).** Round 1 cut the poisonable registry and landed on "read-path re-verify against a composition-injected verifying-key set." Round-2 scouts then broke *that*: there is **nothing persisted to re-verify** — `collective_memory` has no signature/root column (only `source_log_ref`/`source_region` TEXT), the bundle `region_sig` signs the *root* and is never stored per row, and verifying one row needs a Merkle inclusion proof. Worse, `build/verify/apply_replication_bundle` have **zero production callers** — the replication crypto path is unwired. **Ratified re-scope (Option A): the forgery closes at ENTRY** (`verify` refuses a forged cross-team bundle; `apply` never lands it), `team_guard`'s read stays presence-only (13.1), and the read-time row-level guard + attestation persistence ride with 13.3.
- **G4 — where the operator seed lives. STILL BINDING (and now moot for the store).** The seed that derives team **signing** keys must never cross below the `CollectiveMemoryPort`. Under Option A the store doesn't verify at read at all, so it holds **neither** the seed nor a verifying-key set — `verify_*_bundle` takes `base_seed` as a parameter (as 11.2a already does, `bundle.rs:184`) and is exercised at the verify/apply seam in tests. Scouts confirmed the seed isn't even available at the store composition site (`main.rs:2288` builds the store; the operator seed loads ~5000 lines away at `:7481`), which is *another* reason the read-path key injection was the wrong shape — production seed→store wiring is 13.5c's, not 13.2's.
- **G5 — bundle schema evolution.** `CrossRegionReplicationBundle` (`bundle.rs:58-65`) signs `SIG_DOMAIN || schema_version || source_region || root`. **Recommend: extend with `source_team` and dispatch on `schema_version`** — v1 (no team) keeps the byte-exact region path + `derive_region_pubkey`; v2 (with team) adds `source_team` to the signed pre-image + derives the pubkey from `(region, team)`. This mirrors the cohort manifest `SIG_DOMAIN_V1`/`SIG_DOMAIN_V2` dispatch 13.1 already built (`manifest.rs:57-58`) — the house pattern for schema evolution under a frozen v1.
- **G6 — team pubkey is DERIVED, not stored.** A code scout suggested adding a `team_pubkey()` method to `TenantMapPort`. **Reject that** — Fork-4 says the verifier *derives* the pubkey from `(claimed_region, claimed_team)` via HKDF (§15.11:167), it does not look one up. `base_seed` (the operator audit key) threads to the verify path **exactly as 11.2a already threads it** for `verify_replication_bundle(bundle, base_seed)` (`bundle.rs:184`). No manifest pubkey storage, no new `TenantMapPort` method for keys. This keeps the manifest the authority for *placement* and the operator seed the root for *keys* — the two trust roots stay separate (do not cross-wire the pinned cohort-authority key at `maos-cohort/src/pin.rs` with the HKDF-derived team key; they are different kinds).
- **G7 — the region `source_log_ref` residual vs the team forgery. RESOLVED (party-mode 2026-07-17, reversed from the draft).** The draft recommended flipping leg #5 because the (now-cut) registry would have closed both residuals. With the registry gone (G3), **13.2 does not close the region axis at all** — the region `source_log_ref` presence residual's only named successor *was* that registry. **Murat's ruling: do not flip leg #5.** It forges a **`source_log_ref`** (region presence, 11.2b D1) — a different threat on a different axis; leaving it asserting *served* keeps it as an honest document of the still-open region residual. **Add a distinct, new leg `forged-team-stamp-refused`** (same-region cross-team) for the team axis. One leg, one threat, no conflation. **13.2 closes D1 on the team axis only;** the story states plainly that the region `source_log_ref` presence residual **remains open and, as of this story, has no named successor mechanism** (flag it in the threat model) — do not let the epic's imprecise *"closes 11.2b D1"* line imply the region axis is done.

### Preflight resolution record (party-mode 2026-07-17 — Winston · Vex · Murat · John · Amelia, Lunarpulse sign-off)

Discipline: E12-B6 *"a claim standing in for a control"* reflex, non-degradable on 13.1–13.3. Two reversals from the create-story draft, both ratified toward long-term correctness; the other five forks held.

- **G3/G4 REVERSED — kill the trusted-applied-root registry.** Vex broke it: a persisted registry lives in the same Postgres a threat-model-T3 infra credential can write, so the attacker inserts the forged row **and** its matching "verified root" — a lock with the key taped to it. Re-verify-at-read against the derived key is the only anchor that survives, but the store must **not** hold `base_seed` (a signing oracle in the data tier). **Resolution:** the composition root derives team **verifying keys** from the operator seed and injects a public-key set into the store; the read path re-verifies foreign-team rows against those public keys. No seed below the port, no poisonable table. Per-read cost is theoretical at 13.2 (no foreign-team rows until 13.3).
- **G7 REVERSED — do not flip 13.1 leg #5.** With the registry cut, 13.2 no longer touches the *region* `source_log_ref` presence residual at all — its only named successor *was* that registry. Murat's ruling: leg #5 forges a `source_log_ref` (region axis); leave it asserting *served* as an honest document of the still-open region residual, and add a **distinct** same-region `forged-team-stamp-refused` leg for the team axis. **13.2 closes D1 on the team axis only;** the region residual is now open with **no named successor** — flagged in the threat model.
- **Standing findings (held):** (i) this is a **MECHANISM story** — the read-path guard guards nothing in production until 13.3 writes cross-team rows; proven by injection at the store/verify seam, stated in the may/may-not-claim table (John's honesty check). (ii) the forged-team-stamp verifier is **independently derived from the write codec + a positive control** so it is neither a re-call of `verify` nor a reject-everything stub (Murat, R-RG1 shape). (iii) **region-seed compromise is team-wide** (welding over the region seed) — acceptable, but written into the threat model, not discovered later (Vex). (iv) bundle `schema_version` and leaf domain-tag are **two independent version axes** — name them so bumping one never implies the other (Yui). (v) G1 stays *audit crate, fall back to loom-lite if the API-surface gate twitches* — decided at CATCH-0.
- **Scope confirmed: still 6 ACs** (both reversals *simplify* — AC3 shrinks, AC5's leg split stays one AC); **ZERO kernel-core Δ @ 23202; no new crate.**

The read-time D1 residual (**both** axes now), the per-row attestation persistence (`source_team` + `merkle_root` + `region_sig` + inclusion path), and production seed/apply wiring **defer to 13.3**, where the real cross-team write is born and gives the read guard something real to verify. *Option B (build the read guard now as a test-injected mechanism) and a 13.2b split were both on the table; Lunarpulse chose A for the tightest honest scope.*

   - **Frozen versioned grammar, ADR-gated:** `const TEAM_TL_SIGNING_SALT: &[u8] = b"maos.team.tl-signing.v1";` and `const TEAM_INFO_PREFIX: &[u8] = b"maos.team.ascii-v1:";` — each carries the *"Pinned — never change without an ADR; changing it irreversibly re-keys every in-flight team bundle"* tripwire comment (`sealed_export.rs:13-19` idiom), plus a **frozen-encoding test** mirroring `region.rs::encoding_id_is_frozen` (`region.rs:283-288`).
   - **⚠️ `TeamId` does NOT mirror `Region`'s canonicalization — do not add lowercasing.** `Region::canonicalize` trims + lowercases *then* validates, so `US-EAST`/`us-east` derive one key. **`TeamId::new` (`team.rs:17-28`) REJECTS non-canonical input and never normalizes** (*"rewriting signed text would make the authority ambiguous"*). The team weld therefore takes an already-validated `&TeamId` and uses `team.as_str().as_bytes()` (`TeamId` has **no `as_bytes()`** and **no `ENCODING` const**, unlike `Region`). The AC-12 *"two spellings → one key"* property is enforced for teams by **rejection at the `TeamId` boundary**, not by folding inside the derivation.
   - **Sign-only Ed25519, direct RustCrypto — NOT AEAD, NOT `CryptoProvider`.** Mirror `bundle.rs` / `sealed_export.rs`: `ed25519-dalek = "2"` (locked 2.2.0) + `hkdf = "0.12"` + `sha2 = "0.10"` are **already `maos-loom-lite` deps** (`Cargo.toml:29,32,33`) and `maos-audit` deps — **zero new crates**. Do **not** route through `maos-domain::ports::crypto::CryptoProvider` / `RingCryptoProvider` (that is the ring path; the region/team weld deliberately bypasses it — `sealed_export.rs:4`).

   - **Hand-off to 13.3 (stated, not hidden):** the read-time D1 residual on the team axis, the per-row attestation columns (`source_team` + `merkle_root` + `region_sig` + inclusion path), the read-path verify-with-inclusion (`maos_audit::merkle::verify_proof`), and production seed→store + apply wiring all land with 13.3's real cross-team write. 13.2 supplies the `source_team` provenance and the entry-verify those depend on.

4. **Per-team Merkle root independence, proven by the payload-oracle + row-count triple (the 11.2a L3 discipline), not the dedup'd SET-root alone.** Mutating team B's store does not move team A's root. Physical database-per-team (13.1) makes this true by construction; AC4 proves it with rigor.
   - Group leaves by `source_team` and compute the per-team root via `kv_merkle_root` (`leaf.rs:140`), the payload oracle via `compute_kv_payload_oracle` (`leaf.rs:124`), and the row-count. Mutate team B's store; recompute team A's **triple** → all three unchanged.
   - **The SET-root is dedup-blind (`leaf.rs:134-146` delegates to `build_tree`, which sorts+dedups); the payload oracle catches any single-byte within-team mutation; row-count catches duplicate/count drift.** A test that checks only the root would pass a within-team payload mutation — the exact 11.2a L3 gap (`canonical.rs:357-376` `payload_byte_flip_changes_oracle_not_root`). Prove all three.
   - **⚠️ Mixed v1/v2 convergence (Round-2, Murat).** A team store holds v1 leaves (its own rows, `source_team = None`) mixed with v2 leaves (cross-team copies, `source_team = Some`). Prove two regions' stores of the *same* team **still converge** across the mix, and that per-team independence holds when a store contains both — or leaf-v2 quietly breaks 11.2a cross-region convergence for any team that adopts a cross-team copy.

5. **`check-multi-tenant-loom` crypto legs — flip ABSENT → proven, verifier INDEPENDENTLY derived, and the forged-stamp negative is SAME-REGION cross-team (the Fork-4 payoff, not a cross-region tautology).** Reuse the gate's `BindingClass`/`LegResult`/non-vacuity model (`check_multi_tenant_loom.rs:30-104`; each backing test is a single `#[test]`, `"running 1 test" + "1 passed"`). Remove `ABSENT_SUCCESSORS[0]` = `"13.2 per-team cryptographic key boundary"` (`check_multi_tenant_loom.rs:17`).
   - **(a) `forged-team-stamp-refused-at-verify`** — hermetic `Blocking` (pure crypto, no DB, the Fork-4 payoff): **two teams in the SAME region**; team-B builds a v2 bundle claiming `source_team = A` and signs it with team-B's derived key; `verify_replication_bundle` derives team-A's key from `(region, A)` and B's signature **fails** (`BundleError::SignatureVerificationFailed`). ⚠️ **This MUST be same-region** — a forged-stamp leg exercised only across regions is the vacuous tautology ADR-049 rejects (13.1 F9), because `region_guard` already refuses cross-region. Same-region is exactly where Fork-4 earns its keep. Independently derive team-A's expected pubkey from the **write codec** (not a re-call of `verify`) + a **positive control** (team-A signs, verifies OK) so it is neither a codec-tautology nor a reject-everything stub (R-RG1 shape, `sealed_export.rs:367-390`).
   - **(b) `apply-refuses-forged-bundle`** — `Blocking` (hermetic in-memory store, or live): `apply_replication_bundle` on a forged cross-team bundle writes **zero rows** (apply runs only after `verify`); the forged row never lands. This is the entry-closure Option A rests on.

### Traps (each has already bitten this codebase)
1. **Re-rooting every store.** Populating `source_team` on first-party local rows flips them to v2 tags → every team's Merkle root changes vs 11.2a → convergence and every hardcoded golden red. Local rows stay `None` (G2).
2. **The cross-region tautology.** A forged-team-stamp leg exercised across regions proves nothing new — `region_guard` already refuses it. It **must be same-region cross-team** (F9 / ADR-049 "same-region self-comparison = vacuous").
3. **Looking up the team key instead of deriving it.** The manifest owns *placement*, the operator seed roots *keys*; the team pubkey is `derive_team_pubkey(base_seed, region, team)`, not a `TenantMapPort` field (G6). Storing it would recreate the "forgery is a one-liner" hole (ADR-054 §2).
4. **Building a read-path guard (Round-2, the headline).** `collective_memory` persists **no** signature/root column, the bundle sig is over the root (not stored per row), verifying one row needs a Merkle inclusion proof, and `build/verify/apply_replication_bundle` have **zero production callers**. So a read-path re-verify has nothing to verify and guards no production rows. **Close the forgery at `verify` (entry); the read-time guard is 13.3's** (Option A). Do not touch `team_guard`, do not inject keys into the store, do not add a `StoreError` read-refusal.
5. **Adding lowercasing to the team weld.** `Region` normalizes; `TeamId` **rejects** (`team.rs` immutability rule). Fold nothing in the derivation.
6. **Inventing a cataloged `maos-domain` `E*` for the refusal.** `verify` already returns `BundleError::SignatureVerificationFailed`; Option A needs no new error. 13.1's `Tenant*` `StoreError` variants are deliberately *not* cataloged (loom-lite is outside `error-catalog.toml scan_dirs`) — do not break that precedent for a refusal that already has a type.
7. **`check-kernel-baseline` is exact equality** — even a `cargo fmt` reflow of a kernel file reds it. Touch no kernel file (the plan); confirm 23202 at CATCH-0.
8. **A skipped live leg is *unmeasured*, not green** (`check_cross_region_consensus.rs:127`). Provision the substrate (already done) or the leg advisory-greens without proving anything.
