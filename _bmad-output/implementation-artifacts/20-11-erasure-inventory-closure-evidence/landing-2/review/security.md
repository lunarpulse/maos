## O4 halt-fence verdict (primary ask): repair is sound, no bypass found

- `crates/maos-kernel-core/src/halt/mod.rs:540-545` — `invoke_halt` acquires the `closed` mutex **before** any durable write and holds it across TL row (`:556-566`), journal entry (`:568-576`) and registry insert (`:586-601`).
- `crates/maos-kernel-core/src/halt/termination.rs:41-49` — `terminate_spirit` inserts the pid into `closed` **before** `drain_for_spirit`. Therefore: a halt that starts before the close completes fully and is drained→receipted; a halt after the close is refused before any write (`SpiritUnloading`, zero rows/journal — pinned by `crates/maos-kernel-core/tests/halt_unload_fence_20_11.rs:221-253`).
- All terminators funnel through `terminate_spirit` with the **same** `Arc<HaltRegistry>`: unload `crates/maos-kernel-core/src/scheduler/scheduler_loop.rs:561-570`, crash `crates/maos-kernel-core/src/supervision/crash_detector.rs:131`, revocation `crates/maos-kernel-core/src/revocation/applier.rs:151,182`; composition root shares one registry (`crates/maos-bin/src/main.rs:2345-2352, 3029-3039, 3070-3075, 3614-3618`). No second-registry bypass. Residual risks are F3/F5/F6 below.

## Findings

**F1 — Medium — Spirit-forgeable halt-invocation rows → false `unplanned_crash` receipts and attacker-inflated `pending_halts` evidence in the signed erasure proof (GDPR Art. 17 evidence integrity).**
Path: a guest Spirit emits a typed IAC frame with `FrameKind::EpistemicHalt`; the wasm bridge lifts it with a verbatim, unvalidated `halt_id` (`crates/maos-wasm-host/src/frame_bridge.rs:406-412, 616-621` — struct literal bypasses `EpistemicHaltPayload::new`); `deliver_typed` maps the Spirit-chosen kind to TL kind 3 and logs it (`crates/maos-iac/src/adapter.rs:600-603, 622-625, 691-703`). The orphan query treats **any** kind-3 row with a textual `halt_id` as a halt invocation — no origin/writer filter (`crates/maos-audit/src/lib.rs:1814-1817`); payload is typed-reserialized so `terminal_state` cannot be injected (suppression impossible), but invocation-shaped rows are indistinguishable. At uninstall, `close_pending_halts` mints real `unplanned_crash` receipts for them (`crates/maos-bin/src/main.rs:11080-11105`) and they become `RemovalEvidence::Halt` rows counting toward `pending_halts: Removed{n}` (`main.rs:11453-11455`). Exploit: malicious installed Spirit emits halt frames in a loop; impact: inflated/counterfeit removal evidence in a signed bundle the operator publishes as erasure proof, plus TL pollution. Attribution is pid-bound (own Spirit only — no cross-Spirit effect). Fix: reject Spirit-submitted `FrameKind::EpistemicHalt` at ingress (kernel-reserved kind), and/or have `orphaned_halts` filter on a kernel-writer marker (e.g. `origin`/dedicated intent) so only `invoke_halt` rows count.

**F2 — Medium — same forgery with `halt_id: ""` permanently bricks the uninstall/erasure cascade for that Spirit.**
`orphaned_halts` accepts an empty-string `halt_id` (`json_type(...) = 'text'` matches `""`, `crates/maos-audit/src/lib.rs:1815-1817`), but `close_pending_halts` propagates `HaltId::new(...)?` → `Err(HaltIdError::Empty)` (`crates/maos-bin/src/main.rs:11083-11085`) → `work` fails → `Failed` terminal (`main.rs:11470-11496`). One forged row makes every subsequent uninstall of that Spirit fail — a durable denial of the Art. 17 erasure path with no operator remedy. Fix: validate at ingress (F1) and, in `close_pending_halts`, skip malformed orphan ids into an explicit `CoverageGap` instead of `?`.

**F3 — Medium — receipt `frame_id` misbinding race: `insert_frame_event` + `last_frame_id()` readback is not atomic.**
`terminate_spirit` writes the marker row, then reads `tl.last_frame_id()` (`crates/maos-kernel-core/src/halt/termination.rs:62-77, 93-113`; same pattern in `invoke_halt`, `crates/maos-kernel-core/src/halt/mod.rs:556-566`). `last_frame_id()` returns the last insert **by any thread** (`crates/maos-iac/src/adapter/transparency_log.rs:722-725`; cell set at `:1432-1434, 2575-2577, 3181-3182`). Any concurrent TL writer (another Spirit's routed frames, telemetry, parallel unload) that lands between the two calls makes the receipt payload cite a foreign frame — attacker-raceable by a Spirit spamming frames. `planned_unload_receipts` extracts `(halt_id, frame_id)` from the receipt payload (`crates/maos-audit/src/lib.rs:1844-1870`), so erasure `RemovalEvidence::Halt.receipt_frame_id` can cite an attacker-chosen frame while still verifying (membership-only check, `crates/maos-audit/src/erasure/proof.rs:524-560`, `tools/verify-erasure/verify.py:160-219`). Fix: use a returning-id insert (cf. `insert_kernel_event_returning_id`) so the frame id is captured under the adapter's inner lock.

**F4 — Medium — unbounded O(n·m) scan in `orphaned_halts` (TL DoS on the erasure pipeline).**
The CTE `j` scans all kind 3/7/19 rows and the per-halt ownership subquery re-probes it with `ORDER BY a.r DESC LIMIT 1` (`crates/maos-audit/src/lib.rs:1815-1828`); neither `idx_tlog_kind(kind,timestamp_ns)` nor `idx_tlog_boot_pid_ts(boot,pid,timestamp_ns,frame_id)` (`crates/maos-iac/src/adapter/transparency_log.rs:557-577`) serves a rowid-ordered lookup on the materialized CTE, plus repeated `json_valid`/`json_extract` per row. It runs twice per uninstall (`crates/maos-bin/src/main.rs:11108, 11224`). A Spirit inflating kind-3 volume (cheaply via F1's frame path) makes the operator's uninstall/erasure command effectively hang — availability DoS of the right-to-erasure pipeline. Fix: single-pass attribution (window function per `(boot,pid)`), a partial index over kinds 3/7/19, and a row ceiling with explicit pagination/gap.

**F5 — Low — "closed pids never reused" is asserted, not enforced (`allocate_pid` wraps).**
`NEXT_SPIRIT_PID.fetch_add` wraps silently at `u32::MAX` (`crates/maos-kernel-core/src/scheduler/scheduler_loop.rs:30-33`); the invariant lives only in a comment (`crates/maos-kernel-core/src/halt/mod.rs:105-107`, `termination.rs:41-45`). After wrap, a recycled pid is already in `closed` → every halt for the new live Spirit is refused `SpiritUnloading` — a halt silently dropped for a live Spirit. Not Spirit-triggerable (only `load_obj` allocates; loads are operator-driven, 2³² required) — defense-in-depth. Fix: `fetch_update` with wrap refusal, or allocate skipping pids present in `closed`.

**F6 — Low — global `closed` mutex held across TL+journal writes with unbounded Spirit-influenced payload; no length caps on halt payload fields.**
`invoke_halt` holds the process-wide mutex across serialization + TL write + journal + registry insert (`crates/maos-kernel-core/src/halt/mod.rs:540-604`). `EpistemicHaltPayload` has no length limits on `tag`/`policy_id`/`derived_from` (Spirit-supplied provenance) — unlike `RetractPayload`'s 4096-byte cap (`crates/maos-domain/src/frame.rs:225-257` vs `:347-355`). A Spirit supplying multi-MB `derived_from` (`crates/maos-kernel-core/src/capability/working_memory/policy_runtime.rs:134-141`) stalls **all** halt invocations and terminations process-wide and bloats the TL (amplifying F4). Fix: cap payload fields at 4096 like `RetractPayload`; keep lock hold minimal (re-verify under lock at insert).

## Rejected candidates (11)

1. **`SpiritUnloading` info leak** (`crates/maos-domain/src/halt.rs:340-341`, `mod.rs:544-545`): discloses only the caller's own pid (pid is kernel-supplied in `process_scalar_write`, `orchestrator.rs:59-88`); Spirits already know their pid. No cross-Spirit read.
2. **Cross-Spirit halt_id collision suppressing orphans** (`id NOT IN` is boot/pid-global, `lib.rs:1823`): production halt_ids are kernel-minted ULIDs (`policy_runtime.rs:133`); the only Spirit-chosen-id path (F1) cannot inject `terminal_state` (typed serialization drops unknown fields), so the resolved-id set can't be poisoned cross-Spirit.
3. **Verifier forgery via verify.py ↔ merkle.rs divergence**: audited odd-leaf duplication (`verify.py:75-83` vs `merkle.rs:101-107`), empty-tree sentinel, exact-index binding, exclusion adjacency (`verify.py:123-133` vs `merkle.rs:199-215`), canonical signed field set (`verify.py:296-302` vs `proof.rs:296-317, 164-220`) — byte-for-byte consistent; no acceptance gap in either direction.
4. **SQL injection in `orphaned_halts`/`planned_unload_receipts`**: all values are bound parameters (`lib.rs:1829, 1866`); halt_id is concatenated only as an `instr()` argument value, never into SQL text.
5. **pid-0 `lifecycle.journal` echo misattribution** in the ownership subquery: echoes are kind 7 with intent `lifecycle.journal` and the subquery requires `intent='lifecycle.load'` (or k=19); pid-0 halts match no identity row and fail closed (`lib.rs:1818-1822`; `scheduler_loop.rs:745-758`).
6. **`term-` prefix hiding planned-unload receipts** (`lib.rs:1862-1864`): the door path cross-checks `halts_before` and converts any missing receipt into an explicit `CoverageGap` (`main.rs:11055-11073`); counts are evidence-bound, so this only trims evidence, never fabricates closure.
7. **verify.py U+2028/U+2029 canonicalization divergence**: Python `json.dumps(ensure_ascii=False)` does not escape them, matching `serde_json` — no divergence.
8. **verify.py memory blowup**: input read is capped at 128 MiB +1 before parse (`verify.py:330-333`); local operator tool.
9. **Deadlock/poison via `closed` mutex held across the TL write**: no lock-order inversion (nothing acquires `closed` while holding `pending`/`metadata`); an I2 write panic unwinds and releases; poison handled via `into_inner` (`mod.rs:540-545`, `termination.rs:41-45`).
10. **Fence bypass via a second registry**: single shared `Arc<HaltRegistry>` across scheduler/crash/door/orchestrator (wiring cited above); the transient registry in `close_pending_halts` is a separate CLI process with no live Spirits.
11. **`unwrap`/`expect` after serde in touched production code**: none found — every decode site maps errors (`proof.rs:697-729` decode/verify, `lib.rs:1832-1839, 1868-1875`, `main.rs:11083-11121`, `termination.rs:75-79` `to_vec` match). The touched *test* files use `unwrap`/`expect` freely (harness-only, out of production scope).
