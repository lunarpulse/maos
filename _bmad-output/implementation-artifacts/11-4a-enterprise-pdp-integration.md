## Story

**As** the enterprise MAOS operator standing up a compliance-bound deployment (Journey: Reza Cortex / cross-team policy; PRD §Reza, `10-journey-traceability.md:174,178`),
**I want** capability-authorization decisions to be sourced from a **real external Policy Decision Point** (OPA / Cedar / Vault-style) behind an **out-of-kernel `PolicyDecisionPort`** — so my organization's policy (expressed in the PDP's native language, evaluated by the PDP's real engine) governs which Spirits may hold which capabilities — with the integration proven to be **live evaluation, not a hardcoded stand-in**, a **deny rule proven to actually block a capability**, and a **fail-closed** posture when the PDP is unreachable,
**So that** MAOS satisfies the v2.0 "Enterprise Spirit class with PDP integration" commitment (product-scope §70; domain-specific §82; success-criteria v2.0 "PDP integration") **without breaking the v1.0-frozen ABI or drawing the kernel-core budget** — the kernel stays the small, dumb mediator (ADR-006 "the kernel learns nothing"; the operator's policy is the operator's data), and the enterprise's PDP becomes the authority for capability grants while the kernel's hot-path token-verify stays `<5µs` (ADR-030).

### Explicitly NOT in 11.4a (defend at review)
- **SSO / OIDC / SAML identity assertions** and **SSO→capability-token issuance** → **11.4c** (`epic-11…md:48`). 11.4a's decision *subject* is the existing `spirit_pid` (u32) — NOT a federated principal. The port is designed so 11.4c can *layer* an authenticated principal as an additional PDP request attribute, but 11.4a ships **no** identity provider.
- **Encrypted-at-rest memory with org KMS** and **SIEM telemetry export (NFR-Aud-11)** → **11.4c**.
- **The sandbox-escape structural detector (ADR-024, NFR-Sec-3)** → **11.4b** (a *different* out-of-kernel subscriber; not policy).
- **A live interactive approval prompt / approval-resolution UX.** The `ApprovalManager` (`security/approval.rs`) currently **auto-allows** (`:74`) and both `Deny` and `RequireApproval` collapse to `CapError::PolicyDenied` at issue time (`capability/mod.rs:189-197`). 11.4a proves a real *deny* through the **issue path** (`issue_with_mediation`); it does **not** build interactive resolution (out of scope — L5).
- **Shipping three production PDP adapters (OPA + Cedar + Vault).** 11.4a ships the **engine-agnostic port** + **ONE reference adapter** proving real evaluation end-to-end (F3 lean: Cedar, in-process, CI-runnable). OPA / Vault adapters are **additive-per-port** (ADR-010 multi-adapter-per-port) — documented, not built here (unless preflight expands scope).
- **Putting the PDP on the IAC hot path.** ADR-030 forbids it (`<5µs` P99). Decisions are materialized into the read-mostly CoW `cap-policy` snapshot off-hot-path — L1.
- **Any kernel-core edit.** ZERO-Δ (F2). If genuine live per-request evaluation is judged necessary, that is a **preflight FLAG-Winston escalation** (a bounded re-pin at the `capability/mod.rs:188` call site), never a silent kernel edit — L2.

## ⚠️ PREFLIGHT FLAGS (landmines — read first)

### L1 — The PDP MUST NOT be called on the IAC/token hot path (ADR-030 `<5µs` P99).
`cap-tokens` verify is lock-free sharded-atomic `<5µs` (§4.6, ADR-030 Gate). A synchronous OPA/Cedar/Vault call there is orders of magnitude over budget and architecturally forbidden. Decisions are evaluated **off-hot-path** and materialized into the **read-mostly CoW** `cap-policy` snapshot. `evaluate()` stays a table walk.

### L2 — `cap_policy` is kernel-core; only the AUTHORIZED `per_capability_deny` surface may be edited (F2).
`crates/maos-kernel-core/src/capability/cap_policy/` and `capability/mod.rs` are **inside** the counted tree (`check_kernel_baseline.rs`, exact-equality). Preflight authorized **exactly one** kernel-core surface: `OperatorPolicyConfig.per_capability_deny` + the deny-wins `evaluate` arm (F2 FLAG-Winston, re-pinned). Do the PDP wiring at the composition root (`main.rs`) + the new adapter crate + the new port trait. Do NOT touch `capability/mod.rs`'s mediation flow or the other `evaluate` arms. A live per-request eval inside `issue_with_mediation` was **rejected** (F2 rationale + ADR-030 hot-path) — do not add one.

### L3 — A hardcoded decision map is the story's central theater trap ("canned green").
The whole thesis is "decisions from REAL evaluation." An adapter that returns decisions from a `HashMap` literal (not the engine) passes a naïve test and is a **P1** (the 11.2a vacuous-count class). The proven-red MUST be a **policy swap that flips the verdict** — a hardcoded map *cannot* flip when the policy changes. The `pdp-fault-inject` falsifier (AC3) stubs the engine to canned-Allow and asserts the deny test goes **RED**, proving the deny is engine-derived.

### L4 — Fail-open on PDP-unreachable is a P0. Fail closed (F4).
`PolicyDecisionError::{Unreachable,Timeout}` from a *configured* PDP must degrade to **deny** (or freeze last-known-good, per F4), never to permissive defaults. Proven-red: configured-PDP-down → capability **refused**. (Distinct from *no PDP configured* → kernel default, AC1.)

### L5 — The only live allow/deny reachable in prod today is `PolicyTable::evaluate` via `issue_with_mediation`.
`evaluate_with_posture` (`cap_policy/mod.rs:252-294`) has **no live non-test caller**; `ApprovalManager.prompt` **auto-allows** (`approval.rs:74`, `:69` writes `decision:true`). Both `Deny` and `RequireApproval` collapse to `CapError::PolicyDenied` at issue (`capability/mod.rs:189-197`). **Scope the deny-proven-red to the issue path** (`issue_with_mediation` → `Err(PolicyDenied)`); do NOT assume you can observe an end-to-end interactive approval verdict.

### L6 — An external PDP server makes the deny leg advisory-skipped when unprovisioned (F3/F5).
This is the exact trap `check-multi-region-slo` / `check-scale-churn` fall into (their Postgres legs are `skipped` in CI → advisory-only). An **in-process** reference engine (Cedar) keeps the deny tripwire real per-commit. If an external server is chosen, provision it via a `services:` block or accept advisory-only.

### L7 — The engine client crate must be quarantined from the kernel/domain closure.
Add the PDP-engine client crate names (e.g. `cedar-policy`, or the OPA/Vault client) to `FORBIDDEN_CRATES` in `xtask/src/check_dependency_closure.rs:42-53` (checked crates are exactly `["maos-kernel-core","maos-domain"]`, `--edges all` so even a dev-dep leak reds). Add any duplicate-version transitive deps to `deny.toml [bans] skip` with a provenance comment (the Postgres block at `deny.toml:72-97` is the precedent), and its license to `[licenses] allow`.

### L8 — A new adapter crate bumps the workspace count 37→38.
`check-workspace-count` reconciles `Cargo.toml` members against a `<!-- workspace-count-authoritative -->` markdown sentinel. Update the sentinel doc or the gate reds.

### L9 — `check-composition-root-completeness` keys on `*Adapter` re-exported from `api.rs`.
It requires every `*Adapter` re-exported in `crates/maos-kernel-core/src/api.rs` to be constructed **exactly once** in `main.rs`. The external-PDP adapter is NOT a kernel-core adapter — keep it **out of `api.rs`** (or construct it exactly once) so the gate stays green.

### L10 — Do not confuse `ComplianceVerdict` (`maos-compliance`) with authorization.
`maos-compliance::evaluator::ComplianceVerdict {Admit,Reject}` validates ComplianceClaim *envelopes* (signature/fingerprint drift) — an orthogonal concern. 11.4a is **capability authorization**. Do not reuse or entangle it.
