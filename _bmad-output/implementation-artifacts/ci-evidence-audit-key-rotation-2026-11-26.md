# CI evidence audit key: investigation and rotation plan (operator ruling 2026-11-26, item 8)

The key value appears nowhere in this note, in any report or in any log. It is called "the 64-hex key" throughout.

## Findings

1. **The tracked file is a pure leak, not a dependency.** `ci-evidence-audit.key` (repo root, mode 100644, 64 bytes) was committed by `3e332302` ("provisioning: RELEASE_SIGNING_KEY, MAOS_RELEASE_PUBKEY, CI_EVIDENCE_AUDIT_KEY present", 2026-09-24). The runbook (`docs/runbooks/provisioning-checklist.md`) told the operator to generate it as `./ci-evidence-audit.key`, set the secret from it and delete the local copy; the copy was committed instead. A byte search of the whole tree (excluding `.git` and `target`) finds the 64-hex key in exactly one file: that one. It is also in git history from `3e332302` onward; `git rm` does not remove it from history, which is why rotation (not deletion) is the fix.
2. **Nothing reads the tracked file.** Searches over `.github`, `xtask`, `scripts`, `tests`, `crates`, `docs` and `docs-site` for `ci-evidence-audit` find one hit: the runbook's `keygen --output` example. No workflow step, xtask command, test, fixture or gate opens that path. So no reader needs editing and no code change is required for the cutover.
3. **The only production consumer is the secret `CI_EVIDENCE_AUDIT_KEY`**, through the composite action `.github/actions/install-ci-evidence-key/action.yml` (inputs: `secrets.CI_EVIDENCE_AUDIT_KEY`). The action rejects anything that is not exactly 64 hex characters (`::error::`, exit 1), writes it to `$RUNNER_TEMP/maos-ci-evidence/audit-signing.key` (0600 in a 0700 dir) and exports `MAOS_AUDIT_KEY` pointing at it. With an empty secret it only warns and writes nothing. It is used by two jobs in `.github/workflows/discipline.yml`: `check-multi-tenant-loom` (about line 4653; signs) and `check-ship-gate-completeness` (about line 3370; re-verifies).
4. **What the key is.** An Ed25519 seed (the format `maosctl audit keygen` writes, loaded by `maos_domain::audit_key::load_audit_key_seed`). It signs the live-evidence transcript records (`tests/harness/evidence_record.rs::emit`: canonical JSON of `{commit, gate, nonce, test, outcome: "PASSED"}`, signed with `sign_sha256sums`). `xtask/src/evidence_ledger.rs` `EvidenceVerifier` derives the public key from the same seed and verifies each record, bound to THIS build (`GITHUB_SHA`, run id and attempt, nonce). A verified leg is `PROVEN_LIVE_SIGNED`. Without the key a signed leg reprojects to `INDETERMINATE` and `check-multi-tenant-loom`'s required `reza-three-team-three-region-journey` leg is `ABSENT`, which turns `check-multi-tenant-loom`, `v1-0-ship-gate` and `aggregate` red (`docs/runbooks/provisioning-checklist.md` row; `xtask/src/check_multi_tenant_loom.rs:192`).
5. **Old evidence.** Records are bound to a commit, a run and a nonce, are produced and verified inside the same workflow run, and are never re-verified later by any gate. The ledger artifacts of a run (`evidence-ledger-*`, retention 90 days at most) were verified in that run under the old key; after rotation they simply cannot be re-verified by a newer key, which is the same as for any run older than the artifact retention. They stay valid as historical CI records (they prove "ran in this CI job" at that time), so treat every ledger signed by the old key as **legacy: signed by a key that was later disclosed and rotated**, not as forged. Signed ledgers committed in `_bmad-output` (`13-6-evidence`, August 2026) pre-date the CI key (2026-09-24) and were produced with the operator's local key, so they are unaffected. [INFERENCE] Whether any committed post-2026-09-24 ledger is signed by the rotated CI key was not checked: deriving the old public key to compare would have required handling the key value; no gate re-verifies committed ledgers.
6. **Exposure.** Anyone with read access to the repository history can forge a `PROVEN_LIVE_SIGNED` leg for any run until the secret is rotated. The key is not the release-signing key: `RELEASE_SIGNING_KEY` / `MAOS_RELEASE_PUBKEY` are separate secrets and are not affected by this.
7. **Repo side done in this lane.** No reader existed, so no reader was edited. Changed: `.gitignore` (adds `/ci-evidence-audit.key`; `*.key` was NOT added, because other `*.key` names may legitimately be test fixtures), `docs/runbooks/provisioning-checklist.md` (keygen output goes to a `mktemp -d` dir outside the checkout; states the key is never committed and points here). The tracked file itself is still in the tree: `git rm` is the orchestrator's.

## Cutover order (orchestrator)

1. Generate a new key OUTSIDE the checkout: `key_dir=$(mktemp -d) && maosctl audit keygen --output "$key_dir/ci-evidence-audit.key"` (not the operator's `~/.config/maos/audit-signing.key`).
2. **Set the repository secret `CI_EVIDENCE_AUDIT_KEY` to the new file's exact bytes FIRST** (64 hex, no trailing newline shown or added; the action's shape check fails the job on 65 bytes). Do this before merging the PR and before any run that starts after the merge: a run only receives the secret value current at its creation time (the 2026-09-24 provisioning log shows a run created before the secret got it EMPTY).
3. Delete the local copy (`rm -r "$key_dir"`).
4. Merge the PR that `git rm`s `ci-evidence-audit.key` (it also carries the `.gitignore` and runbook changes). Because nothing reads the tracked file, the merge order is not coupled to any workflow: workflows that need the key read only the secret.
5. Workflows that fail without a valid secret: `check-multi-tenant-loom` (hard fail: leg ABSENT; also fails on a malformed value), `check-ship-gate-completeness`, and through them `v1-0-ship-gate` and `aggregate`. After step 2 and the merge, confirm one run where `check-multi-tenant-loom` reports `reza-three-team-three-region-journey` `PROVEN_LIVE_SIGNED` with the new key (the step log shows the secret as `***` and passes the 64-hex check).
6. Record the rotation date in the provisioning checklist's provisioned list (secret creation timestamp from the secrets API; never read the value).
7. History: the old key stays in git history. Rotating the secret is what removes its value; history rewrite is not needed for security and is not proposed. If the operator wants the old blob gone anyway, that is a separate, disruptive decision (force-push of main) and is not part of this ruling.
