## Correctness findings and recommendation

[INFERENCE] Scheduling counterexamples and architecture compatibility judgments below are source-derived analysis, not executed concurrency/adversarial-scheduler tests. Executed measurements and checks are separately identified above.

1. **BLOCKER — AC2.3 / D-17-4-FW-01:** a finite time-hold/capacity-triggered reorder buffer cannot guarantee same-emitter cross-tag order. Schedule: sequential A then B writes; A-topic forwarder is delayed beyond the hold while B reaches delivery; B is released, then lower-seq A is delivered late. There need be no broadcast lag and no loss. Counting `late` cannot undo the inversion. Repeating this schedule can exceed the 1% inversion allowance. Evidence: story `17-4-hooks-observer-and-activity-corpus.md:88-89`; independent per-topic channels `crates/maos-kernel-core/src/telemetry/mod.rs:40,92-125`. Recommendation: one broad receiver and one sequential delivery path, without tag forwarders/reorder hold. **Needs operator ruling**, because it changes the exact ratified kernel charter (`17-4-flag-winston-decision.md:16-19`) and measured ceilings/baseline treatment. Replace the reorder-bypass mutation with a deterministic adjacent-delivery inversion; the current bypass plant is scheduling-dependent and may naturally receive correctly ordered events.
2. **SHOULD-FIX — CR-4 / AC2.2:** epistemic policy rules are halt-policy configuration, not a complete declaration of valid scalar tags. Store validates nonempty tag, not membership (`crates/maos-capability/src/working_memory/store.rs:43-62`), and publishes every successful write (`crates/maos-kernel-core/src/capability/mod.rs:228-234`). Declared-only subscription makes undeclared writes permanently invisible without `Lagged` accounting; the corpus declares every tag and cannot catch that coverage gap (story `:59,87,107`). This conflicts with the intended broad scalar trajectory (`architecture-maos-minimal-opus/4-kernel-design.md:474-476`, ADR-035 `12-architecture-decision-records.md:488`, NFR-Obs-3 `prd/non-functional-requirements.md:103`). Broad receiver removes the tag-discovery requirement; retain Observer registration, Running filtering, and Observer's existing principal-scope filtering. Add an undeclared-tag regression. Removing this compromise restores the existing broad-observation intent, but the kernel mechanism still requires the operator charter ruling above.
3. **SHOULD-FIX — AC4.1 / seq documentation:** assigning seq under the store lock does not order the subsequent publish outside the lock. Concurrent caller X can allocate seq 0, stall before publish, while Y allocates and publishes seq 1 first. Evidence: store `:69-79`; adapter `capability/mod.rs:228-234`; story `:104`. Call it **store-write order**, not global publish order. One channel orders successful send linearization exactly, and therefore preserves one thread's sequential set_scalar calls across tags (Tokio shared tail lock `broadcast.rs:631-666`); it does not enforce global seq order or define a total causal order for concurrent threads using the same Spirit ID. The AC4 corpus correctly gates only actual same-emitter program-order pairs, not independent emitters. Retain seq for unique event identity, duplicates and unchanged-valued repeated writes. Seq does not prove float identity: retain `value_bits` oracle plus float-roundtrip codec. No additional kernel edit is needed merely to correct the terminology; global store-seq delivery would require a larger separate serialization design/ruling and is not needed for per-thread causality.
4. **SHOULD-FIX — delivery gate / new API:** proposed firehose cannot land under the two-test-literal charter, nor can the current surface baseline remain untouched. Measured +13 physical/+11 tokei versus the ratified +2/+2; actual service-boundary run rejects changed struct hash. Explicitly amend the charter/re-pin set and approve a private-layout surface-baseline refresh, rather than claiming that an unenumerated inherent method means no gate change. Classify `subscribe_all` as data-movement alongside existing inherent methods, even though this walker does not enumerate it.

**Sound:** one receiver gives one honest aggregate `Lagged(n)` counter across tags (proven capacity-2 regression), not a receiver-times-event sum. Retained events remain in exact send order despite skipped gaps. One receiver replaces the multiple forwarders and reorder queue; it still needs prompt draining/bounded sequential delivery and the corpus's missed-rate gate: its 2048 capacity is aggregate, unlike 2048 per topic, so burst loss must be measured, not assumed. Keep existing narrow-topic subscriptions; thus I7 per-Spirit fanout, ADR-035 dedicated scalar data and NFR-Obs-3 broad/narrow topic filtering remain compatible when the composition-root pump routes only registered Observer subscribers. This does not introduce generic non-scalar telemetry. Existing `drop_count` semantics are unchanged by the prototype: an event delivered to the broad receiver with no exact-topic receiver still increments that historical topic-path counter. It must not be used as total-observation loss; receiver `Lagged(n)` is the pump loss oracle. Existing no-subscriber and exact-topic receive tests passed unchanged apart from seq literals. `#[serde(default)]` permits old payloads but their default seq 0 is not unique; identity claims apply to live store-generated events in the same root, not legacy/synthetic payloads or root restarts.

Recommendation: approve the measured single scalar firehose kernel amendment, retain seq as identity/store-write metadata, eliminate the time-hold reorder and CR-4 tag-discovery compromise, then amend the story/corpus controls accordingly. This prototype tests the transport, not the future production HookPump or final 20-scenario loss/causality floor.
