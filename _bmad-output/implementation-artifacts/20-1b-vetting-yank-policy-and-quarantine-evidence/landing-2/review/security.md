## Findings

### F-1 — HIGH (known and filed, but the filed row under-states the reload surface) — Yank-policy quarantine is one-shot: any reload sheds the fence and nothing ever re-applies it
**Where:** `crates/maos-kernel-core/src/capability/mod.rs:140,366-381` (pid-keyed in-memory set); `crates/maos-kernel-core/src/scheduler/scheduler_loop.rs:573` (unload unconditionally clears the fence); `crates/maos-registry/src/yank.rs:147-156` (cursor advances on `Verified`; no replay of consumed sequences); `crates/maos-bin/src/yank_policy.rs:87-105` (the only yank-path fence setter, reachable only via `on_yank`/`reevaluate_at`); no load-time yank check exists anywhere in `maos-bin` admission (grep for `yanked` in `crates/maos-bin/src` finds only the fixture smoke at `main.rs:9190-9203` and search flags); `crates/maos-kernel-core/src/hot_swap/coordinator.rs` (no quarantine/fence consult at all).

**Exploit/impact:** With `MAOS_YANK_POLICY=quarantine`, the fence is the *only* enforcement of a publisher withdrawal against an already-installed Spirit (install-time refusal covers only new installs, `maos-cli/tests/spirit_install_20_1.rs:404`). The fence dies on: (a) daemon restart; (b) operator unload+load; (c) hot/cold swap (successor pid is never fenced — for a *same-version* swap nothing re-fences either); (d) a Spirit forcing its own unload (crash disposition bindings `crates/maos-bin/src/supervision.rs:1064-1113`, Worker exit → `supervision.rs:2608-2612`) followed by any operator/topology reload. In every case the yank row is consumed (cursor monotonic, `observed` keyed by the dead pid, `yank_policy.rs:133-172`), so the withdrawal is never re-applied — a compromised, yanked Spirit regains full mediated capability. There is no auto-respawn (crash dispositions are Nack/Reassign/Escalate, `maos-kernel-core/src/supervision/disposition.rs:28-55`), so the Spirit needs an operator or boot reload — routine events.
The CRL path is **not** affected: `rejects_manifest_locked` (`revocation/rules.rs:76-92`) refuses any matching class/version-range load regardless of action, and the 1 s `RevocationPoller` re-applies the local CRL after restart. The asymmetry is the finding: the same quarantine effect is durable for CRLs and one-shot for yanks. The deferred row (`docs/../deferred-work.md:1563`) files "restart or crash-restart reloads the Spirit unfenced" with cursor-no-replay named, but the unload/swap legs and the CRL-vs-yank asymmetry are not spelled out.

**Fix sketch:** persist the yanked `(spirit_id, version)` set (cursor file or sidecar) and refuse/fence at load admission the way `rejects_manifest_locked` does, or route the yank quarantine through a durable local CRL exactly as `auto-revoke` already does (`yank_policy.rs:479-513`).

### F-2 — MEDIUM — Hostile registry grows the audit transparency log indefinitely with unsigned rows
**Where:** `crates/maos-registry/src/yank.rs:136-160` (a `Rejected` disposition never advances the cursor; a sequence anomaly sets `resync`); `crates/maos-bin/src/yank_policy.rs:401-414` (`on_rejected` writes a TL row on every call); interval clamped 30–300 s (`yank.rs:249-265`).

**Exploit/impact:** A registry needs no key: park one entry at `cursor+1` with an invalid signature. Each poll it is delivered again (`since` = stuck cursor), rejected again, and journalled again — one `yank-rejected` TL row per poll per parked row, forever (~288–2,880 rows/day each), unbounded disk growth in the SQLite TL that legal-hold/erasure machinery depends on, plus full-suffix re-download/re-verify per poll (`resync` forces `since=0` fetches while an anomaly row stays ahead of the cursor). Verified rows behind the parked one still apply, so this is flooding/DoS, not suppression. (This is the residue of L1 P1/P2: the poller no longer wedges, but "never advance past a rejected row" trades the wedge for per-poll re-journalling.)

**Fix sketch:** dedup rejected rows by `(sequence, reason-hash)` in `YankRuntime` — the exact pattern the revocation poller now uses (`revocation/poller.rs:47-68`) — or keep a separate rejected-high-water that suppresses duplicate `yank-rejected`/`yank-sequence-anomaly` rows while still never trusting them for the verified cursor.

### F-3 — LOW — No operator reversal path; door status cannot distinguish quarantine from pause
**Where:** `set_quarantined(pid,false)` has exactly one caller — unload (`scheduler_loop.rs:573`); the verb table has `revocations-import`/`revocations-list` only (`crates/maos-bin/src/verbs.rs:157-159`, `operator_door.rs:2859-2906`); `operator_door.rs:1044-1046` reports `fenced = capability.is_paused(pid)`, and `is_paused` is `quarantine ∨ pause` (`capability/mod.rs:356-363`).

**Impact/semantics:** A mistakenly quarantined Spirit can only be restored by unload (process destruction). For a CRL quarantine, reversal additionally requires `forget` (rules only, `rules.rs:58-73`) — forgetting the CRL does **not** lift the fence, and re-apply then reports `AlreadyApplied` only until forget, so the state machine is coherent but entirely implicit. The `fenced` readback conflates a resumable director pause with a sticky quarantine, which matters because resume lifts one and not the other (`quarantine_fr13_20_1.rs:492-517` proves resume keeps quarantine).

**Fix sketch:** an audit-journaled `quarantine-release <pid>` door verb plus a distinct `quarantined` boolean in the status readback.

### F-4 — LOW — Revocation-poller failure dedup hides the identity of persistent failures
**Where:** `crates/maos-kernel-core/src/revocation/poller.rs:47-68`.

**Analysis:** Only the first failure's error text ever prints; later failures — possibly a *different* error (fetch vs trust-anchor vs CRL parse vs `apply_crl`) — print nothing until the single recovery line with a bare count. Telemetry still records every failure, but under one coarse `ErrorKind::App` bucket (which also mislabels transport errors — pre-existing kind choice). Not a suppression of the failure itself (count + recovery exist), but error *transitions* are invisible on stderr during a persistent fault. AC12 explicitly rules "telemetry unchanged", so this is a deliberate trade; the residual is observability only.

**Fix sketch:** print when the error string changes (not only on the first failure), or include the last error text in the recovery line; split transport vs parse error kinds.

### F-5 — LOW (documented boundary, restating precisely) — The fence mediates tokens only
**Where:** enforcement is exactly three sites — `issue_with_mediation` (`capability/mod.rs:207-209`), `verify_and_audit` (`:323-327`), `recheck` (`:348-352`). Not fenced: `set_scalar`/telemetry publish (`:283-303`), DRR dispatch (`scheduler_loop.rs` `pick_next_spirit` — quarantined Spirits stay Running and keep receiving slices), hook dispatch, IAC egress (KQ2 explicitly priced and not selected, `deferred-work.md:1565`), and T3 Worker in-container activity (`deferred-work.md:1562`).

**Impact:** "Quarantine" is no-new-tool-calls, not isolation: a quarantined Spirit keeps executing, publishing telemetry, and (where IAC sends require no token) messaging. This matches the ruled shape and the two filed rows; recorded here so the FR13/I5 flip (still `asserted`, `docs/invariants/I5.md:11`) is not read as claiming isolation.

## Rejected candidates (investigated, no credible path)

1. **`spirit.quarantined` spoofing by a Spirit** — no Spirit-reachable writer with an arbitrary intent string: the WIT ABI carries `intent` as an enum (`wit/spirit.wit:265-293`), the journal adapter is typed (`journal/mod.rs:177`), memory/telemetry writers use fixed intents, and both production writers are pinned by FR4 shape entries (kind 7, `spirit_pid == row pid`, `quarantined: Bool` — `crates/maos-audit/src/fr4_classifier.rs:418-433`, both classifier cases green in `fr4_classifier_16_2.rs:287-300`). Payload carries id/pid/bool only — nothing to redact.
2. **Hostile/compromised registry quarantining chosen Spirits (forged/replayed rows, cross-publisher)** — `verify_entry` (`yank_auth.rs:105-135`) binds name, version, reason, registry URI, origin and key into the signed scope; Publisher origin must equal the pinned publisher key, Vetter origin must be enrolled in the local keyring and verified against the *local* audit root. Replay can only reproduce legitimately-signed scopes (same name/version/reason) — it cannot mint a yank for a never-yanked Spirit; URI rebinding and wrong-publisher rows are rejected (witnessed, `yank_policy_20_1b.rs:371-410`). Vetter cross-publisher authority is by-spec (AC7.1; noted in L1 triage).
3. **Stale quarantine entry fencing an innocent reused pid** — pids are monotonic (`scheduler_loop.rs:31-33`) and the single `spirits.remove` site clears both fences (`:572-577`); no other removal path exists in the scheduler.
4. **unwrap/expect after serde in the new paths** — none: `yanks_since` maps errors (`client.rs:107-115`), cursor load matches (`yank.rs:333-348`), `installed()` maps parse failure to `SignatureInvalid` (`yank_policy.rs:112-131`), `local_yank_crl` propagates strings. The one known red (`main.rs:11090` `unwrap_or_default`) is pre-existing from `5ff0ead1` and filed (`deferred-work.md:1566`). The `panic!` in `journal_terminal_observation` is serialization of a plain struct (L1-dismissed).
5. **Cursor rollback/poisoning (L1 P2) left unfixed** — fixed in tree: schema-v2 cursor bound to `registry_uri` with replay-on-mismatch (`yank.rs:333-348`), head-behind-cursor refusal both in the poller and client (`yank.rs:126-134`, `client.rs:108-112`, test `authenticated_head_rollback_never_mutates_or_resets_cursor_d3_f5`), contiguity/anomaly/resync (`yank.rs:136-160`), per-Verified-row cursor save (`:147-156`), `/tmp` fallback removed (`:273-293`). Residual = F-2 and the inherently unsigned head (AC15-authenticated heads landed separately).
6. **Yank row wedging the poller (L1 P1)** — fixed: `on_yank` returns `Ok(Rejected)` for unverifiable rows (poll continues; other rows still deliver), `on_poll` failure no longer blocks fetching (`yank.rs:107-110`), `reevaluate_at` isolates per-Spirit errors (`yank_policy.rs:212-263`). The cost of "rejected never advances the cursor" is F-2.
7. **Auto-respawn resurrecting a quarantined Spirit by itself** — no same-pid respawn binding and no new-pid auto-reload exist (`supervision.rs:1064-1113`, dispositions at `disposition.rs:28-55`); resurrection needs an operator/boot reload, which is F-1's surface.
