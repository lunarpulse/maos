# Blind Hunter — adversarial review of 62faff63 (20-1b landing 1)

Method: bmad-review-adversarial-general over diff.patch, no story/spec read. Source files checked at the commit where a claim needed call-site proof. No cargo/tests run. Findings are unranked per skill contract; "conf" is my confidence it is real.

- **Single non-delivering yank row wedges the whole poller (head-of-line block).** `crates/maos-registry/src/yank.rs:99-118` (`poll_once`) returns `Err` on the first `on_yank` failure *without advancing the cursor*, and `crates/maos-bin/src/yank_policy.rs:194+` (`on_yank`) returns `Err` for any `verify_entry` failure. Concrete trigger: the registry server (with `--vetter-keyring`) accepts a Vetter-origin yank for `pkg@V`; the daemon has `pkg@V` installed *without* `vetting.json` (the normal public-untrusted install) → `keyring == None` → `verify_entry(.., None, ..)` → "unauthorized vetter yank: no enrolled keyring" → `Err` on every poll, forever. All later yanks for every other Spirit are never delivered. Same wedge for: authorization `issued_at > daemon now` (clock skew), vetter later revoked (re-verified at the *current* `now`), keyring file gone, `apply_crl` error under auto-revoke, unreadable `installed-index`. Each retry also re-journals `yank-poller:remote-yank-propagated`. Fix: classify per-entry failure as terminal-skip (journal a rejection row, advance cursor) vs transient (retry), never block later sequences. conf 0.85.

- **Cursor advances on the unauthenticated, unsigned `sequence` of rows for Spirits that are not installed → permanent yank blindness.** `yank.rs` `poll_once` sets `cache.last_seen_ns = entry.sequence`; `on_yank` returns `Ok(())` (no verification) when the Spirit is not installed / version differs. `sequence` is server-assigned and not covered by the `YankAuthorization` signature. A registry (or any MITM on the plaintext link; AC15 explicitly not claimed) can emit one row with `sequence = u64::MAX` for any uninstalled name; the cursor is persisted and `yanks_since` filters `e.sequence > since_ns` forever. Related: a restored/reset registry (`yanks.json` lost, sequence restarts at 1) is silently invisible until it passes the stale cursor — no server epoch/id in cursor or response. And the cursor file is a single global path (`cursor_file_path()`), not keyed by registry URI: switching `MAOS_REGISTRY_URI` applies registry A's sequence to registry B. `HOME` unset falls back to world-writable `/tmp/.local/share/maos/registry/yank_cursor.json`, a local user can plant `u64::MAX`. Fix: advance cursor only past rows whose signature verified or that are provably not applicable *and* bound the jump (e.g. cursor ≤ previous+len); key cursor by registry identity + server epoch; reject sequence regressions loudly. conf 0.75.

- **`on_poll()` runs before the fetch and aborts the poll on any local error, coupling yank delivery to unrelated local state.** `poll_once` calls `self.observer.on_poll()?` first; `YankRuntime::reevaluate_at` (`yank_policy.rs:99+`) uses `?` inside the per-spirit loop for `installed()` errors (e.g. one corrupt/mis-signed install → `SignatureInvalid`), unreadable `installed-index.json`, missing audit key seed, unreadable `vetting.json`, and every non-Expired/Revoked `VettingRejection` (including `MalformedClaim` from a *missing keyring file*). Consequence: one broken install or deleted keyring (a) skips re-evaluation of every other running Spirit that poll, and (b) skips `fetch_yanks` entirely. Also an expired/revoked Spirit whose keyring is deleted is never flagged (fail-open: `MalformedClaim` is an error return, not `vetting_revoked`). Fix: evaluate per spirit, collect errors, continue; run fetch regardless of `on_poll` outcome. conf 0.8.

- **Partial-failure ordering in `reevaluate_at` re-emits terminal observations every poll.** `observe_running_spirit(..)` (journals) runs before `policy_request(..)?` and `observed.insert(key)` only happens after success; if `policy_request` fails (auto-revoke `apply_crl` error) the observation row is journaled again on every cadence tick until success; `observed` Mutex is held across `block_in_place`/`block_on`. A panic inside `journal_terminal_observation` (`panic!` on serialize error) would poison `observed` and make every later poll `Err`. conf 0.6.

- **Vetting state is read from a live, mutable keyring path with no integrity anchor — rollback of revocations is undetectable.** `InstalledVetting { keyring_path }` (install.rs) stores a canonicalized path to the operator's keyring and `verify` re-reads it on every boot and poll. The keyring's events/revocation lists are individually operator-signed but the *set* is not anchored: restoring an older valid keyring (or truncating `attestation_revocations`, which is `#[serde(default)]`) silently un-revokes a vetter key/attestation for running-promotion re-evaluation, `verify_installed`, and `on_yank` vetter-yank verification. No hash/sequence pin of the keyring at install time or high-water mark. Also `vet revoke` is a non-locked read-modify-write of that file (lost update with a concurrent enroll/revoke). conf 0.55.

- **Any enrolled vetter can withdraw any Spirit from any publisher; vetter authority is not tied to an attestation it issued.** `YankAuthorization::verify` Vetter arm only calls `keyring.verify_enrollment(root, vetter_key_id, public_key, issued_at, now)`; nothing checks that this vetter attested that package/version/publisher. One compromised/malicious enrolled key can yank (and, with `MAOS_YANK_POLICY=auto-revoke`, terminate + permanently CRL) arbitrary installed Spirits. Fix: require a matching, still-valid attestation by that `vetter_key_id` for (name, version, publisher) on the server and daemon. conf 0.6.

- **auto-revoke is applied to non-yank causes with origin `RegistryYank`, contradicting declared `RefuseAtNextLoad` semantics.** `reevaluate_at` calls `policy_request(.., YankOrigin::Vetter, "expiry-lapse"|"vetting-revocation")`; under `AutoRevokeRequested` this builds `local_yank_crl(.., "registry-yank: expiry-lapse")` with `RevocationOrigin::RegistryYank` and applies a persistent `name =version` rule. An attestation that merely expired (claim carries `RefuseAtNextLoad`) now terminates a running Spirit and permanently revokes that exact version — re-issuing a fresh attestation can never restore it — with an audit label that says "registry yank" when no yank exists. Only the Quarantine variant is tested (`expiry_and_vetter_revocation_observe_once...`); auto-revoke on expiry/revocation is untested. conf 0.5.

- **`YankAuthorization` has no audience, expiry or nonce, and zero clock-skew tolerance.** Signed message binds name/version/reason/origin/key/vetter id/issued_at but not the registry or sequence; `issued_at > now` is a hard reject (`"not yet valid"`) with no skew window, so any CLI-clock-ahead-of-server (remote registry) fails spuriously, and the daemon re-checks at its own clock (feeds the wedge above). Replays across registries serving the same name/key/version are accepted; every distinct re-signing (new `issued_at`) appends a *new* `YankEntry` (dedup is on identical authorization bytes only), so a key holder can grow `yanks.json` unboundedly; `install()` downloads `yanks_since(0)` (entire history) every time, and each row is processed/journaled by every daemon. conf 0.5.

- **Artifact binding is checked against the sidecar's own `artifact_bytes`, not the artifact actually run/upgraded to.** `GatedManifest::bind_registry_package_at` (admission.rs:498) verifies sidecar signature + manifest bytes equality only; the sidecar is a public file, so a modified artifact next to the genuine manifest + genuine `signed_package.json` binds the *genuine publisher's* storage identity (reads that publisher's memory namespace). Likewise `enforce_vetted_upgrade_precondition` (main.rs ~190) builds `VettingSubject::from(&package)` from the sidecar and never compares it to the on-disk artifact (`verify_installed` does that comparison for the install path; these two paths don't). The attestation's artifact-swap defence is therefore nominal on `maos run <path>`, operator-door load and upgrade. Absent `signed_package.json` also silently yields the bare (unpartitioned) identity. conf 0.55.

- **Uninstall erases both the publisher pin and the immutability record, and does not take the new cross-process lock.** `uninstall_package` (storage.rs:283) renames away the whole `installed/<name>/` tree; `check_publisher`/`install_package` derive pin + immutability *only* from files in that tree, so uninstall → reinstall by another publisher/with changed bytes succeeds (the local pin lives only as long as the install). `uninstall_package` takes `INSTALLED_UNINSTALL` (in-process) but not `.mutation.lock`; a concurrent `maosctl spirit install` process hitting the "reuse existing generation" branch can rewrite `installed-index.json` to point at a generation the other process just removed (that branch writes no files and doesn't revalidate). conf 0.45.

- **Same-package reinstall from the same registry is rejected as "immutable" if the URI string differs.** `install_package` compares `stored_origin != *origin` by full `RegistryOrigin::Remote{uri}`; localhost vs 127.0.0.1, http→https, port change, trailing path all make an *identical* package an `ImmutableVersion` error (and the vetting.json comparison makes adding/removing an attestation to an installed version a hard error). AC14 wording aside, this makes idempotent reinstall/promotion impossible without uninstalling — which then erases the pin (previous finding). conf 0.4.

- **Server-side version mutability and non-atomic package writes remain.** `put` accepts re-publish of an existing version by the pinned key (`let _ = Self::check_publisher(..)?` discards the "existing" hit) and `write_package` overwrites `manifest.toml`/`artifact.bin` with plain `fs::write` *before* the atomic `signed_package.json`; readers (`get_manifest`/`get_artifact`, `install`) take no lock, so they can observe new `artifact.bin` with old `signed_package.json`. Signature checks catch the tear, but the result is a transient hard failure; and a yanked version can be silently replaced under the same version string (yank row stays, but bytes differ from what vetters/yank authorizations referenced). conf 0.4.

- **Registry-installed Spirits lose existing private memory on upgrade (no migration).** `storage_identity` switches from bare `spirit_id` to `name:sha256(publisher)[..16]` for every Spirit that has a `signed_package.json`; `bind_storage_identity` is now called with the new key in `load_admit_start`, so memory previously written under the bare name by registry-installed Spirits becomes unreachable with no migration or warning. conf 0.4.

- **`MAOS_YANK_POLICY=quarantine` is an operator-visible no-op with no runtime disclosure; poller failure modes are silent.** `env_contract.rs` registers it `UserFacing`; the daemon prints nothing about the active policy or that quarantine has no isolation effect (docs-only disclosure). The removed `eprintln!("YankPoller wired/disabled")` lines mean there is no log that the poller is running at all; `MAOS_REGISTRY_YANK_POLL_INTERVAL_S=0` now silently disables local attestation expiry/revocation enforcement too (previously only yank polling); the poller is created only if the registry connected *or* installs existed at boot (installs made afterwards need a restart); `default_installed_manifests()?` at boot makes a malformed `installed-index.json` abort daemon startup. conf 0.5.

- **Running-spirit ↔ install matching is by name+version only.** `YankRuntime::installed(name)` / `reevaluate_at` treat any Running SCB with the same `spirit_id` and `class.version` as the registry install; a locally developed Spirit with the same name/version is quarantined/revoked on a yank or vetting lapse of the registry package. conf 0.35.

- **Operator audit key is reused as CRL signer, vetter-keyring root, and attestation-revocation signer.** `local_yank_crl` signs with the audit key seed; `vet revoke` and `install` derive the same root. One key now spans audit, CRL and vetting trust domains; compromise or rotation of the audit key has an unplanned blast radius. conf 0.3 (design smell).

- **`verify_installed` swallows `exists()` errors for the promotion file.** `promotion_path.exists()` returns false on permission errors; for non-`public-vetted` manifests an unreadable `vetting.json` is treated as "no promotion" and the verification (including revocation) is skipped. conf 0.35.

- **Test-quality issues.** (a) `crates/maos-registry/tests/yank_auth_20_1b.rs` has parallel `#[test]`s that `set_var`/`remove_var` `HOME` and `MAOS_REGISTRY_*` with no shared lock (the `maos-bin` file does use an `ENV` mutex) → racy/flaky, and the in-process server threads read env concurrently. (b) No test covers the wedge scenarios above (vetter-origin yank on an unpromoted install; invalid row followed by valid row; `u64::MAX` sequence row; cursor from a different registry), no server-side test with a keyring rejecting a *revoked* or *not-yet-enrolled* vetter (only the keyring-less server is exercised), no auto-revoke-on-expiry test, no test that `on_poll` failure still delivers yanks. (c) Tests named `*_ac8` (`signed_yank_decisions_..._ac8`, `policy_outcomes_are_distinct_ac8`) assert only the typed *request*, not the AC8 quarantine effect that is declared unclaimed — name/coverage-matrix wording risks being read as AC8 evidence. (d) `registry_publishers_cannot_share_principal_spill_ac10` ends with a magic `3 + len*2 <= 255` check using a 128-char name (hashed path); the 93/94 boundary and the bare-vs-hash collision are untested; the "second publisher" is simulated by re-signing the sidecar, not by a real two-publisher install. (e) `yank_cadence_20_1b` asserts `polls == 2` and a 35 s ceiling, which does not detect a poller that runs *slower* than the clamp floor within 35 s but is wall-clock sensitive on loaded CI; adds ≥30 s serial wall time per run (budget exception 39 s).

- **Smaller notes.** `YankCache.apply`/`save_cursor(.., 0)` drop the yank count (field now always 0). `vet issue` attests any publisher-signed package without running admission and without checking that `--vetter-key-id` is enrolled for the supplied key (failure surfaces only at install). `serde_sig64/pubkey32` now use `deserialize_bytes` — any previously persisted array-encoded CBOR CRL/keyring would depend on `serde_cbor` coercing arrays; only a bytes→roundtrip test was added, no legacy-array decode test.
