# Blind Hunter — 20-1b AC15/F5 (f9921251), adversarial review

Method: diff-first (`/tmp/rev201b.diff`, `/tmp/rev201b-tests.diff`), then each claim checked against HEAD source. Read-only; nothing executed. `[INFERENCE]` marks anything not directly observed in code. Line numbers are HEAD.
Verdict on the core design: TLS client/server, URI-bound pin, nonce-bound envelope, literal-loopback gate and both-end dev handshake are sound as written. The findings below are real gaps, ordered by what I would fix first.

---

## B1 — Operator CA is *added to* WebPKI roots, not substituted
- File: `crates/maos-registry/src/security.rs:273-279` (`client_tls`).
- Evidence: `roots.extend(webpki_roots::TLS_SERVER_ROOTS…)` runs unconditionally, then `ca_certificate` certs are `add`ed. Setting `[registry].ca_certificate` therefore *widens* trust to every public CA plus the private one; it never narrows.
- Consequence: an operator who pins a private CA for an internal registry still accepts any publicly-trusted certificate for that hostname. The envelope key bounds integrity, but transport confidentiality (publish/deprecate request bodies, bearer-free but sensitive) is exposed to any mis-issuing public CA. The doc (`SECURITY.md`) and the test `interception_untrusted_ca_is_refused_ac15` only prove a *stranger private* CA is refused, so this is invisible to the suite.
- Fix: `if let Some(path) = ca { roots from path only } else { webpki roots }`. Keep the `empty certificate chain` error. State the rule in SECURITY.md.
- Failing-before witness: serve with a leaf issued by a *second* rcgen CA whose root is injected into the client via a test-only root-store hook (or, simpler, assert `client_tls(Some(ca))` root count == certs in file, not `+ webpki_roots::TLS_SERVER_ROOTS.len()`). The count assertion needs a `pub(crate)` accessor; otherwise unit-test inside `security.rs`.

## B2 — `verify_head` hard-fails any signed request that lacks a `params` member
- File: `crates/maos-registry/src/security.rs:170-190` (`struct Request { method, params: Params }`, `params` not `Option`/`#[serde(default)]`).
- Evidence: `verify_response` calls `verify_head` for *every* signed exchange once the signature verifies (security.rs `verify_response` → `verify_head(request, …)`). The streamable transport's legacy session path posts `{"jsonrpc":"2.0","method":"notifications/initialized"}` with no `params` (`crates/maos-mcp/src/transport/streamable_http.rs:162`). That body fails `serde_json::from_slice::<Request>` ⇒ `authentication(missing field params)`. Same for `params` given as array/null, or a `name` containing a JSON escape (`#[serde(borrow)] &str` cannot borrow an escaped string).
- Consequence: today the registry server only speaks the modern `tools/call` path, so tests are green; the first time the transport falls back to legacy initialize (CR-1/CR-2 re-probe, `streamable_http.rs:136-140,190+`) every call errors as an "authentication" failure, which will be misdiagnosed as an attack. Verification is also coupled to parsing unrelated request shapes it does not need.
- Fix: make `params` `#[serde(default)] Option<Params>` (and use `Cow<str>`/owned `String` for `name`), and return `Ok(())` whenever the method is neither `registry.yanks_since` nor `tools/call`+name match. Only a *matching yanks_since request that is malformed* should be an error.
- Failing-before witness: unit test `verify_head(br#"{"jsonrpc":"2.0","method":"notifications/initialized"}"#, br#"{}"#, None)` must be `Ok`; and one with `"name":"registry.yanks_s\u0069nce"` must still select the yank rule. Both fail at HEAD.

## B3 — Client cursor ahead of the registry head wedges yank sync permanently
- File: `security.rs:212-225`; `handlers/yanks_since.rs:14-16`.
- Evidence: server head = `entries.last().sequence` (0 when empty). Client requires `head == since + n_entries`. If the poller's persisted cursor (`yank.rs` `cursor_file_path`, schema v2, keyed only by URI) is greater than the server's head (registry store restored from backup / re-created under the same URI / yank journal compacted), the response is an empty list with `head < since` ⇒ `yank list does not reach authenticated head` on every poll, forever. Previously this returned an empty list.
- Consequence: fail-closed is defensible, but it is a silent, unrecoverable DoS of the yank channel with a misleading error, and it also masks a genuine rollback signal as a generic auth failure. Nothing logs "server head N < cursor M".
- Fix: distinguish `head < since` as a typed `RegistryError` ("registry head regressed: cursor M > head N; operator must reset cursor") surfaced by the poller (do not advance, do not silently loop); keep `head != next` for the gap/stripped-entry cases.
- Failing-before witness: storage with 2 yanks, client `yanks_since(5)`; assert the error text names regression (today: generic "does not reach authenticated head"), plus a poller test that the journal row says rollback.

## B4 — Daemon wiring (`main.rs`) has two divergent config parsers and no test
- Files: `crates/maos-bin/src/main.rs:3197` (`RegistrySection::resolve_from_env_and_disk`, lenient: bad hex/tier silently ignored) vs `main.rs:3232-3238` (`install::operator_config`, strict, `crates/maos-registry/src/install.rs:312-368`).
- Evidence: the stderr banner (`main.rs:~3285`) prints `registry_cfg.{tier_floor,require_server_tier_signature}` from the lenient parser while the *enforced* client config comes from the strict one. Divergences: invalid `org_signing_pubkey` (lenient: ignored → banner says none; strict: boot abort); `tier_floor = "bogus"` (lenient: `parse_tier` fallback; strict: error); booleans-as-strings; `MAOS_REGISTRY_URI` env overrides `registry_cfg.uri` but `security.uri` (the pin) is read only from TOML (`security.rs:from_operator`) ⇒ an env-supplied URI can never satisfy the binding and the daemon aborts. Also behavior change: this branch previously degraded to Null with a warning; it now `?`-aborts the whole composition root on any mismatch.
- Consequence: operators see a banner that does not describe the policy actually enforced; env URI override is dead for https; daemon boot hard-fails instead of the earlier fail-soft. No test exercises the daemon path (`grep MAOS_REGISTRY_URI crates/maos-bin/tests` only hits `installed_spirit_dispatch_20_1.rs`, which is not TLS).
- Fix: build `registry_cfg` and the client config from the *same* `operator_config()` result (or make `RegistrySection` call it); print the enforced values; either document that `MAOS_REGISTRY_URI` must equal `[registry].uri` when pinned or add `MAOS_REGISTRY_URI` to the binding input explicitly (env URI + TOML key with equal URI). Decide and test fail-closed vs warn-and-Null explicitly.
- Failing-before witness: maos-bin integration test booting the daemon with an https `[registry]` (rcgen CA, pinned key) and asserting the poller banner `registry-fetch=enabled`; second case with env URI ≠ TOML URI asserting the documented outcome; third with bad `org_signing_pubkey` asserting banner == enforced value.

## B5 — AST teardown guard has silent bypass shapes and a weak floor
- File: `crates/maos-bin/tests/root_shutdown_unload_16_3.rs:64-180` (guard), counts at `:163-168`.
- Evidence / holes:
  1. Release detection matches only a bare call `drop(audit_tx)` (`visit_expr_call`, `path.is_ident("drop")`). `std::mem::drop(audit_tx)`, `let _ = audit_tx;`, `drop(audit_tx.clone())`-then-leak, or moving `audit_tx` into a spawned task/closure are invisible to the AST pass **and** to the text cross-check (`line.trim() == "drop(audit_tx);"`, `:~170`), so the assertion message "a new macro or release shape needs an explicit AST audit" is not actually enforced for those shapes.
  2. `releases >= 7` / `drains >= 11` are floors: deleting an arm's release+drain together (or adding a release without a drain) still passes; only an *unjoined* release trips.
  3. `release_audit_tx_holders!()` is recognised only as `Stmt::Macro`; as a tail expression it is not a join, so a later drain in that block would assert-fail (fail-closed, fine), but an invocation inside an `if`/`match` arm expression without braces is also unrecognised. More importantly the macro *body* is checked by a whitespace-stripped substring `"yank_poller_task.shutdown().await;drop(audit_tx);"`, so a body that reorders to `drop(audit_tx); … shutdown` containing the substring elsewhere (e.g. in a comment-like string token) could pass. [INFERENCE: token-stream `to_string` of a string literal would also match].
  4. Join recognised only as an expression *statement* `yank_poller_task.shutdown().await;` — `let _ = yank_poller_task.shutdown().await;` or inside `tokio::join!` breaks it (fail-closed), not a soundness issue.
- Consequence: guard catches the regression it was written for (a plain `drop(audit_tx)` with no prior join) but gives a false sense of completeness for new release shapes.
- Fix: (a) count *all* occurrences of the identifier `audit_tx` as a moved/dropped value via a `visit_expr_path` pass: assert every path-use of `audit_tx` in the root `fn main` is either a `.clone()` receiver, a by-reference arg, or one of the audited drops; (b) replace floors with `assert_eq!(releases, 7 + macro_invocations_accounted)` pinned to the measured value (the story already pins 10+5 test counts); (c) compare macro body token *sequence* (first two statements) rather than substring.
- Failing-before witness: temporary mutation corpus in the test itself: parse three small synthetic sources (`std::mem::drop(audit_tx)` w/o join; drop in sibling branch of the join; reordered macro) and assert the visitor flags each. Current visitor passes the first.

## B6 — Response status and non-session headers are not covered by the envelope
- File: `crates/maos-registry/src/http.rs:~175-200` (client) vs `Claim` (`security.rs:97-105`): the claim binds URI, nonce, request hash, response-body hash, head. Not bound: HTTP status, `Content-Type`, the returned `response_header` (`Mcp-Session-Id`).
- Consequence: a party that can present a valid WebPKI certificate (B1 widens this set) can rewrite a signed `200` to `404` while the session header is present, driving the transport's "404 with session ⇒ reinitialize" branch (`streamable_http.rs` `legacy_call`), or substitute the session id the client will use afterwards. It cannot forge body content, so impact is availability/session-fixation inside the legacy path. Low, but the envelope claims "authenticated response".
- Fix: add `status: u16` (and, if the session header is consumed, its value hash) to `Claim`, bump `version` to 2, verify in `verify_response`.
- Failing-before witness: `Attack::WrongStatus` responder fixture (valid envelope, status 404) expecting `authentication`; today the status is passed through unauthenticated.

## B7 — Missing negative tests for the focus-list URI/loopback matrix
- File: `crates/maos-registry/tests/registry_tls_20_1b.rs:266-290` (only 5 URIs) and `:786-815`.
- Gaps (behaviour verified correct by reading `canonical_uri`/`literal_loopback`, but unpinned): uppercase host, `:443`/`:80` explicit default port, trailing-dot host, `[::ffff:7f00:1]` (IPv4-mapped loopback must be refused: `Ipv6Addr::is_loopback` is false), `127.0.0.2`/`[::1]` positive cases, `127.1` (url normalises → `as_str != uri`), path `/mcp/`, `/mcp%2e`, duplicate slashes, plus a server-side `--bind 0.0.0.0:0 --dev-http` refusal and `--dev-http` + `--tls-*` conflict (`server.rs` args match). Also no "not-yet-valid" certificate, no wrong-TLS-version test, no test that `--uri` host ≠ cert SAN is detected at startup, no env-URI-mismatch test (B4), no yanks `since` > head test (B3), and no stale-replay-of-previous-signed-response test (nonce is covered only by `WrongNonce`, not by "valid envelope for a prior request replayed after this one").
- Fix: table-driven `canonical_uri`/`literal_loopback` unit tests in `security.rs`; one replay responder (`Attack::ReplayPrior`).
- Failing-before witness: these are mutation witnesses — flip `literal_loopback` to `ip.is_loopback() || mapped` or drop the `url.as_str() != uri` clause and require a red test.

## B8 — Private-key custody is partial
- Files: `security.rs:232-246` (`private_key_file`), `server.rs:~286-300` (args), `server.rs:103-113` (`with_tls`).
- Evidence / consequences:
  1. `key_outside_store` is applied only in `RegistryServerArgs::run`; the public `SpiritRegistryServer::with_tls` / `with_server_signing_key` library entry points skip both the mode/uid check and the outside-store check (the test `private_key_custody_refuses_group_or_world_access_ac15` calls `with_tls` directly, so the TLS key is checked there, but the *signing seed* given programmatically is never checked).
  2. Mode `& 0o077` also rejects `0440` root-owned group-readable secret mounts (k8s `fsGroup`, systemd `LoadCredential`) with a message that does not name the observed mode/owner; uid must equal euid, so a root-run service reading a service-user key fails.
  3. Seed text read into a `String` (`server.rs` signing_key block) is never zeroised; `key_outside_store` canonicalises *before* open (a symlink swapped between check and open is a TOCTOU, [INFERENCE: low value, operator-owned dir required]).
  4. The same Ed25519 seed signs tier attestations (Story 7.2) and now response envelopes and is the pinned trust root: one key, two roles. Domain separation exists for the envelope (`maos.registry.response.v1\0` prefix) but the tier-attestation preimage is not shown to be disjoint; [INFERENCE] confirm it cannot be a 32-byte SHA-256 output the attacker can induce.
- Fix: move the checks into `with_tls`/`with_server_signing_key` file-loading helpers (take paths, not bytes); include `mode={:o} uid={}` in the refusal; wrap seed in `zeroize::Zeroizing`; document/assert key-role separation or derive a distinct envelope key.
- Failing-before witness: library-level test that a 0644 signing-seed path given through the public API is refused; unit test for message content.

## B9 — Per-connection TLS/HTTP error log is unauthenticated, unbounded stderr
- File: `crates/maos-registry/src/server.rs:210` (`eprintln!("maos-registry: connection error: {error}")`).
- Evidence: every failed TLS handshake / scanner hit prints one line from a worker thread; there is no rate limit. Pre-handshake TCP connects cost a thread (bounded by `MAX_CONNECTIONS`) for up to the 5 s request deadline.
- Consequence: log flooding and journald pressure from any internet-reachable registry (the TLS mode removes the loopback restriction); also the Plain 503 path deliberately writes nothing for TLS, so overload is observed only as TCP resets.
- Fix: count-and-summarise (e.g. at most 1 line per source IP per minute) or demote to `tracing` debug; consider a shorter pre-handshake deadline than `REQUEST_DEADLINE`.
- Failing-before witness: test spawning N bad TLS connects asserting ≤ K stderr lines.

## B10 — Portability / feature-matrix claims unverified in the evidence
- Files: `crates/maos-registry/Cargo.toml` (`default = ["tls"]`, `rustix` feature `process`), `http.rs` and `server.rs` `#[cfg(not(feature = "tls"))]` statement attributes on `if` expressions, `crates/maos-spirit-cli/Cargo.toml`.
- Evidence: SECURITY.md itself says macOS compilation is unverified. No `--no-default-features` build of `maos-registry` or `maos-spirit-cli` appears in the commands list I could see (`ac15/commands.md`, filenames in the ac15 dir show only clippy/focus runs). `#[cfg(not(feature="tls"))] if … { return Err }` (http.rs) relies on attribute-on-expression-statement acceptance; `HttpStream::Plain` is built `let mut` in both cfgs (unused-mut warning risk under `-D warnings` on the tls build is avoided only because the TLS arm needs `mut`). `maos-bin` forwards `maos-registry/tls` only under `network`, so an air-gapped maos-bin build links `maos-spirit-cli` without TLS (intended) — but any workspace-wide `cargo build` unifies features back on; no test asserts the air-gap build contains no rustls (`cargo tree -e features -i rustls` witness).
- Fix: add to the CI recipe `cargo check -p maos-registry --no-default-features`, `cargo check -p maos-spirit-cli --no-default-features`, and an air-gap `cargo tree -p maos-bin --no-default-features -i rustls` expecting "not found"; run the macOS job before claiming AC15 green.
- Failing-before witness: the three commands above (any compile error or rustls appearing is the failing evidence).

## B11 — Smaller defects / nits
1. `RegistrySecurityConfig::from_operator` (`security.rs:~25-60`) derives `Deserialize` without `deny_unknown_fields` on a *shared* `[registry]` table, so `signing_key = "…"` / `development_htpp = true` typos are silently dropped. Failure is closed for https (needs key) but a misspelled `ca_certificate` yields "unknown authority" with no hint. Fix: validate known-key set inside `from_operator` against the union of daemon+security keys.
2. `ca_certificate` relative path is resolved against CWD (SECURITY.md concedes this). Reject non-absolute at `from_operator`, don't document it.
3. Server `handlers/yanks_since.rs:14` now reads the entire yank journal from disk per call (`yanks_since(0)`), O(total yanks) per poll per client; and any response >64 MiB is refused by the client (`http.rs` length cap), so once the *filtered* result is small this is fine, but server CPU/IO is now unbounded in journal size. Fix: add `RegistryStorage::yank_head()` and filter in storage.
4. `server.rs:956` allows `development_http` with `addr.ip().is_loopback()` computed from `listener.local_addr()`; an IPv4-mapped dual-stack listener reports `::ffff:127.0.0.1` and is refused (conservative, fine) but the error text "requires TLS or explicit literal-loopback" does not tell the operator which condition failed.
5. `main.rs` first-arm join added at `:9297` is correct, but the final tail join at `:9708` plus arm joins make `shutdown()` idempotence load-bearing (`PollTask::shutdown` takes `task` Option — it *is* idempotent; add a one-line test since the guard assumes it).
6. The `declared_capable_cohort_worker_prerequisite_never_green_skips` test (`root_shutdown_unload_16_3.rs:2312-2335`) re-execs `current_exe` with a hard-coded test path; if that test is renamed the child runs 0 tests, exits 0 and the control fails with a misleading "silently skipped T3". Assert the child's stdout contains `1 passed|failed` or `running 1 test`.
7. Fixtures: key/cert names are labelled `test-only-key.pem`/`test-leaf.pem` (good) and generated per-run by rcgen; no committed key material observed. `Certificates::new` makes the CA `BasicConstraints::Unconstrained` and the leaf without EKU, so the EKU/key-usage path of webpki is never exercised.

## Checked and found sound (no finding)
- SNI/hostname: `ServerName::try_from(host)` from the canonical URL host; IP literals use IP SAN verification; rustls default time validation (expired witnessed).
- Redirect/downgrade: no redirect following; `https`→`http` impossible (scheme fixed from `self.url`); status ≠ 2xx without envelope is refused when a key is configured; `https` requires a key at construction (`http.rs:new`).
- Dev mode both-end: client sends `X-Maos-Registry-Development: true` only for `http`; server 403s any mismatch in either direction (`read_request_headers`); `localhost` and DNS aliases are refused at client (`literal_loopback`), server bind must be a loopback IP.
- Canonicalization: `url.as_str() != uri` rejects uppercase host, default port, userinfo, query, fragment, non-`/mcp` path, IDN/percent aliases; trailing-dot host is accepted by the URL parser but is not a valid rustls `DnsName` [INFERENCE: rustls-pki-types rejects it], so it fails closed.
- Envelope: signature over SHA-256(domain-prefix ‖ CBOR(claim)) with ring (canonical-S enforced), request/response hashes from the bytes the client sent/received, nonce 32 bytes from `SystemRandom`, `deny_unknown_fields`, duplicate envelope header refused, empty-vs-omitted `entries` distinguished (missing `entries` is a parse error; empty list requires `head == since`).
- No `unwrap`/`expect` after serde in production paths of the diff (`security.rs`, `http.rs`, `server.rs`); all go through `map_err`. Test code uses `unwrap` on fixtures only.
