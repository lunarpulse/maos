- C. (Round 3 wording, supersedes rounds 1 and 2) Revocation, stated in terms of the last published set that contains the key K: a successful refresh revokes K only when the set it publishes omits K. A fetch can obtain a set containing K, the issuer can then withdraw K, and that in-flight fetch still completes and renews K's TTL from its completion. K therefore verifies until the first successful refresh that returns a set without K and never past the TTL counted from the completion of the last successful fetch whose set contained K (7 days at the maximum TTL, in monotonic time, plus any host suspension in wall time: the monotonic clock does not count suspend, so the TTL stretches over a suspend). TTL/2 plus the idle tick is a scheduling target, not a completion bound; when the minimum refresh equals the TTL the idle-only path can expire the keys before the next fetch completes (fail closed, unhealthy). An attacker who can block the fetch (not break TLS) can keep a withdrawn key valid for the full TTL. The round-1 text "3.5 days" was wrong. ### Lane Q — the contested reissue proof and the documents (`CARGO_TARGET_DIR=/mnt/build/cargo-maos-e232q`; records `proven-red/review4/Q-*.txt`, markers `E232-PLANT-r4-Q<n>`)

It now OBSERVES the contention: the cohort state is built over a `CheckpointSink` (an audit sink); the reissue's `MemberReissueAccepted { version: 2 }` append runs under `cached`, before the manifest replacement and before any purge, so it is the earliest point at which the reissue is inside the contested section, and the sink reports it over a channel. Only then is the admission released. Final state asserted: no obligation queued, `authorize_reply_send` false for the grant, capacity free (256 new ids admit). The checkpoint wait is a bounded `recv_timeout(SAFETY)` that fails the test.
