## Story

**As** an operator answering a GDPR Article 17 request on a MAOS Host that runs a collective (Loom) tier,
**I want** the erasure cascade to account for every registered backend and to report exactly what it did and did not erase — including the collective tier — and legal hold to be a control I can place, list, release, and rely on,
**so that** the signed proof-of-erasure I hand a regulator is an artifact derived from what actually happened, rather than a structurally-unconditional `completed: true` over stores the cascade never touches.

## The live defect, in code (verified 2026-07-25 at `595e8453`, scout-reported and re-checked)

Four independent paths by which the shipped cascade reports success it did not achieve. **None of these involves the collective tier.** They are the reason this story exists.

- **D-1 — the teardown attestation is self-certifying.** `crates/maos-bin/src/main.rs:8100-8104` calls `ForgetCascadeAttestation::from_outcome(REQUIRED_STORES.iter().map(...).collect(), ...)` — it passes the **required** set *as* the **covered** set. `from_outcome` then computes `completed = REQUIRED_STORES.all(|req| stores_covered.contains(req))` (`crates/maos-audit/src/erasure/regional_teardown.rs:87-89`). **`completed` is unconditionally `true` by construction** and can never be `false` on this path.
- **D-2 — a store in that required set is never erased.** `REQUIRED_STORES` (`regional_teardown.rs:49`) contains `"shared"`, but `forget_with_reason` never touches the Shared tier, and `crates/maos-kernel-core/src/memory/shared.rs` **has no delete method at all** (complete API: `open`/`write`/`read`/`scan` at `:41,123,153,191`). The signed receipt asserts coverage of a store with no erase path.
- **D-3 — a legal-held principal yields a signed success and exit 0.** `crates/maos-bin/src/main.rs:7981-7986`: `Ok(ForgetOutcome::Suspended { hold }) => { eprintln!(...); }` — that is the entire handling. The principal is **not** pushed to `all_principal_ids` (contrast `:7955`), execution falls through to build and Ed25519-sign the proof (`:8018-8079`), and `main.rs:4873-4877` prints `{"status":"uninstalled",...}` and returns `Ok(())` → **exit 0**. (The one-shot `forget` path gets this right — `main.rs:4894-4899` exits 3. The uninstall path does not.)
- **D-4 — `deleted_entries` is an intent count, not an effect count.** `crates/maos-kernel-core/src/memory/private.rs:345-348` increments `count` from an in-memory `remove` whose return value is discarded (it fires even when the key was absent); `:357-361` then attempts `fs::remove_dir_all` and **swallows the error** (`if let Err(_e) = ... { // v0.5 acceptable: partial cascade }`). The already-incremented count becomes `ForgetReceipt.deleted_entries` (`memory/mod.rs:572,591-597`) and `CategoryStatus::Removed { count }` in the signed proof (`main.rs:8019-8023`) — **a signed proof-of-erasure over bytes still on disk.**
- **D-5 (supporting) — a comment that contradicts its own code.** `memory/mod.rs:507-508` promises *"P4: a scrub/marker failure is propagated and the frame is NOT attested as redacted."* `:525-527` does `let _ = self.transparency_log.insert_distillate_redaction_marker(...)` and then pushes the frame into the attested-redacted list at `:528` unconditionally.

**And the control that would have caught all of this does not run.** `REGISTERED_ERASURE_BACKENDS` (`memory/mod.rs:30-35`) promises in its own doc comment that *"a new backend can never slip through unaudited."* Its only consumer is `crates/maos-audit/tests/multi_backend_erasure_test.rs:149`, and **that file is never executed by CI**: `.github/workflows/discipline.yml` contains 40 `cargo test` invocations, **all** of the form `-p <crate> --test <named-test>`, with no `--workspace`, no `--all`, and no nextest. The entire existing GDPR evidence base — `multi_backend_erasure_test`, `erasure_smoke_test`, `erasure_sla_test`, `gdpr_cascade_test`, `gdpr_cascade_corpus_test` — is **unrun**. This is instance **#22** of *a claim standing in for a control*.

## Acceptance Criteria (6)

**AC1 — The proof-of-erasure is derived, not asserted.**
Close D-1 through D-5 so that no signed artifact can claim coverage the cascade did not achieve.
- `run_uninstall_cascade` (`main.rs:7911`) accumulates the **actually-covered** store set from the cascade's own results and passes *that* to `ForgetCascadeAttestation::from_outcome` (`main.rs:8100-8104`). `completed` must be capable of being `false`.
- The `"shared"` entry in `REQUIRED_STORES` (`regional_teardown.rs:49`) is reconciled: either the Shared tier gains an erase path, or the category is recorded as **`CategoryStatus::CoverageGap { reason }`** — the honest-partial vocabulary **already exists** at `crates/maos-audit/src/erasure/proof.rs:22-26` (`Removed` | `VerifiedEmpty` | `CoverageGap`); do not invent a new one. Prefer `CoverageGap` and file the Shared-tier erase gap with a named owner (see *Residuals*); do **not** widen scope to build a Shared erase path here.
- D-3: a `Suspended` outcome inside `run_uninstall_cascade` produces a **non-success terminal state** — the principal is recorded, the proof is not signed as complete, and the process exit code distinguishes it (see AC5).
- D-4: `private.rs` counts **effects**. Increment only on a confirmed removal; propagate or record the `remove_dir_all` failure rather than discarding it.
- D-5: the redaction-marker failure is propagated exactly as its own comment at `:507-508` already promises, or the comment is corrected — the two must agree.
- **Proof obligation:** each of D-1/D-3/D-4 gets a test that is **red at HEAD** before the fix and green after. A fix without a proven-red predecessor does not discharge this AC.

**AC2 — The collective tier is a REGISTERED erasure backend whose partition is proven, not asserted.**
Add the collective tier to `REGISTERED_ERASURE_BACKENDS` (`crates/maos-kernel-core/src/memory/mod.rs:35`) and discharge it under the **disjoint-union partition invariant** already built at `crates/maos-audit/tests/multi_backend_erasure_test.rs:146-168` (`covered ⊎ retained == registered`) — either *proved-erased* or *proved-principal-empty*.
This **discharges 13.1's F16 argument**, which has been the load-bearing and untested assumption since 13.1 (`13-1-multi-tenant-loom-physical-tenant-wall.md:13,:63` promised a "prove the collective tier principal-empty" test that never shipped; `multi_backend_erasure_test.rs` contains **zero** occurrences of `"collective"`).

⚠ **(a) The discharge must be a PROOF, not a label — the existing `"shared"` discharge is a null control (instance #23) and must not be copied.** `multi_backend_erasure_test.rs:103-114` plants its canary in the Shared tier under **`MemoryNamespace::Coordination`** — a *non-principal* namespace — then `:141-144` asserts that row **survived** the forget and pushes `"shared"` into `proved_principal_empty`. That proves the *opposite concern* (no over-erasure of legitimate cross-Spirit data, per ADR-026); it never writes principal data to the tier and never scans for any. Swap `MemoryNamespace::Coordination` for the principal namespace on `:110` and the write **succeeds** (`memory/mod.rs:743` is a bare delegate with no rejection), the forget still ignores it, `shared_store_contains` still finds the canary, and **the assertion still passes** — green in both worlds.
  **Therefore the collective discharge must:** (i) attempt a principal-shaped write **at the collective tier's own entry point** and assert it is *refused* (`reject_principal_collective` fires) — not merely that some unrelated row behaved; (ii) scan the real store for principal-shaped content and assert absence; and (iii) be **falsified** before it is trusted — neuter the guard, confirm the leg goes red for *that* reason. A leg that passes with the guard removed discharges nothing.

Two contradictions of Decision D must be resolved, not narrated:
  - **(b) The store schema contradicts the kernel partition.** `crates/maos-loom-lite/src/schema.rs:166-193` round-trips `MemoryNamespace::Principal { principal_id, schema }` to and from the `namespace_detail` column (test at `:253-256`), while the kernel refuses that namespace at all six collective entry points (`memory/mod.rs:242,306,351,745,805,859`). Either it is dead code — delete it and strengthen the partition claim — or it is reachable, in which case it is the leak.
  - **(c) The replication apply path bypasses Decision D entirely.** `apply_verified_replication_bundle` calls `schema::parts_to_namespace` (`crates/maos-loom-lite/src/replication/bundle.rs:681`), which reconstructs `MemoryNamespace::Principal` (`schema.rs:189-196`), then writes via `write_with_source_attested` (`bundle.rs:781`) — which has **no `reject_principal_collective`**. A signed bundle can land principal-namespace PII in `collective_memory`, and there is no erase path for it. Close the bypass at the apply seam (fail-closed, typed refusal), and prove it with a negative.
  ⚠ **`REGISTERED_ERASURE_BACKENDS` is a kernel-core line-count trap — see Trap 1. Read it before editing that line.**

**AC3 — A single-store collective erase contract, out-of-kernel, with the chokepoint honestly re-stated.**
Add an erase operation to `CollectiveMemoryPort` (`crates/maos-domain/src/ports/collective_memory.rs:93`) and implement it on `LoomLiteAdapter` (`crates/maos-loom-lite/src/adapter.rs:81`) and `LoomLiteStore`. Constraints, all load-bearing:
  - **Keyed by the store's own addressing, not by principal.** `collective_memory` has **no `principal_id` column** (`schema.rs:31-146`), Decision D says it never will, and the `principal_index` address book can never return a collective address (it is populated only from the `MemoryNamespace::Principal` write arm, `memory/mod.rs:716-740`). An erase-by-principal contract is **unimplementable**; do not fake one.
  - **Guarded.** `LoomLiteStore::erase` invokes `team_guard` exactly once before querying, like `write`/`read`/`scan`. This makes the guard's call-site count **four**, which reds a `Blocking` gate — see AC6 and Trap 2. Update `crates/maos-loom-lite/tests/read_path_chokepoint.rs:105-112` **in this story, with the fourth site named**, never at review. Routing the erase through the deliberately-unguarded `pool()` (`store.rs:1145-1149`) to dodge that count is **forbidden** — it is precisely the *"do not preserve a claim by routing around the owner"* shortcut the epic prohibits at `:45`.
  - **Erasure vs. CRDT-LWW resurrection.** The write path is a conditional LWW upsert (`store.rs:534-573`). A hard `DELETE` leaves no tombstone, so a later replication apply carrying the old leaf takes the plain-`INSERT` branch — the `ON CONFLICT` guard never fires — and **resurrects the erased row**. Either ship a tombstone the LWW rule respects, or record the resurrection window as an explicit typed residual with a named successor. **A silent resurrection is a ship-blocker.**
  - **Merkle consequence, stated and proven.** Deleting a leaf moves all three legs of the shipped per-team oracle (`kv_merkle_root`, `compute_kv_payload_oracle`, `row_count` — `crates/maos-loom-lite/src/replication/leaf.rs:253-276`, asserted at `tenant_wall_live.rs:577-583,636-641`). Prove the post-erase triple is re-derivable and that the `per-team-merkle-independence` leg still holds; do not leave the root silently moved.
  - **Zero Spirit-facing reach — the authority argument.** Erasure is an **operator** action executed at the composition root under operator authority, not a Spirit capability. It is therefore **not** added to `SpiritMemoryView` (`memory/for_spirit.rs`), **not** added to the three `MemoryTier::Collective` trait arms, and **not** given a `Scope`. A static control must prove no Spirit-facing path reaches it. This is the whole reason the out-of-kernel route is legitimate rather than a bypass (see AC6 Δ posture).

**AC4 — Legal hold becomes an operable, fail-closed control.**

Add the operator surface (`maosctl` subcommand(s) reusing the `MAOS_ONE_SHOT` dispatch idiom at `crates/maos-cli/src/subcommands.rs:1245-1265`).
  - **(b) The hold cannot fail open.** `SCHEMA_SQL` runs `CREATE TABLE IF NOT EXISTS legal_holds` in `main` on **every** adapter open (`transparency_log.rs:294`), and `attach_global_legal_holds` repairs that by `DROP TABLE main.legal_holds` (`:1060`) — but it is called from exactly one site under one condition (`main.rs:2624`, `if audit_db_path != memory_db_path`). SQLite resolves unqualified names `main`-first, so a process that opens a shard **without** attaching (e.g. `crates/maos-bin/src/escape_detector_consumer.rs:56`) re-creates an empty `main.legal_holds`; a hold written there is invisible to the attached connection and **`is_under_legal_hold` returns `false` → the principal erases**.   - **(c) Backup/DR implication recorded.** Post-attach the team shard no longer contains `legal_holds` (`:1060`), so a team-shard backup (`crates/maos-cli/src/backup.rs:62-95`) does **not** carry holds. State this in the runbook — it is the NFR-Ops-9 implication the epic names at `:155`.

## Traps (each one would be discovered mid-implementation otherwise)

**Trap 1 — `REGISTERED_ERASURE_BACKENDS` is a rustfmt line-count trap that silently breaks the ZERO claim. ⚠ READ BEFORE EDITING.**
`crates/maos-kernel-core/src/memory/mod.rs:35` is **91 characters**. There is no `rustfmt.toml`, so `max_width = 100`. Appending `, "collective"` (+14) yields **105 > 100**, and rustfmt wraps the single line into ~6 — **+5 kernel-core `src` lines**, moving the baseline off 23228. `check-kernel-baseline` counts raw lines (`count_rs_lines`), and E12-B4 made `cargo fmt --check` a gate, so leaving it unformatted is not an option.
**Resolution, in order of preference:** (i) register a name that fits the remaining **9 characters** — `, "loom"` is 8 chars → 99 total, one line, ZERO preserved, and it names the actual backend crate (`maos-loom-lite`); (ii) if a longer name is judged necessary for clarity, that is a **+5 measured re-pin requiring FLAG-Winston** and it is *not* covered by the operator's "out-of-kernel, no re-pin" ratification — **stop and escalate rather than absorbing it**. Measure the formatted result; do not predict it.

**Trap 2 — the `three-site-chokepoint` leg reds the moment this story lands.** `BindingClass::Blocking`, so it hard-fails CI regardless of substrate. Planned in AC6; listed here because it is the highest-probability mid-implementation surprise and the epic never mentions it.

**Trap 3 — the sync/async bridge makes a naive collective erase report `Unreachable` 100% of the time.** `forget_with_reason` is a **sync** kernel method called from inside `async fn main` on a tokio worker thread (`main.rs:4887`, `:7950`), **not** inside `spawn_blocking`. `LoomLiteAdapter` bridges via `block_on_or_typed` → `handle.block_on(fut)` (`crates/maos-loom-lite/src/adapter.rs:59-78`), whose own doc says the supported topology is *inside* `spawn_blocking`; `block_on` on a runtime thread panics, `catch_unwind` swallows it, and the caller gets `CollectivePortError::Unreachable { reason: "collective-tier runtime bridge unavailable (nested runtime or shutdown)" }` (`:73-77`) — typed, silent, and always. **The collective erase must be sequenced from an async context or inside `spawn_blocking`.** This is production wiring, not a test artifact.

**Trap 4 — `insert_kernel_event_returning_id` panics on write failure.** `crates/maos-iac/src/adapter/transparency_log.rs:1129-1160` — `Err(e) => panic!(...)`, documented as the I2 binding. The cascade calls it at `memory/mod.rs:455,485,586`. An orchestrator that journals per-backend results through this path turns an audit-write failure into a **process panic mid-cascade, after some data is already deleted** — the worst possible partial-failure shape. AC5's `failed` path needs an explicit position on this.

**Trap 5 — the redaction filter runs over the forget payload before it is journaled.** `transparency_log.rs:1136` redacts before the INSERT, and the `principal.forget.held` payload embeds `principal_id`, `reason`, and `case_ref` (`memory/mod.rs:446-452`). The audit row AC5 relies on to prove `held` may be journaled with its distinguishing fields scrubbed. Worth one test in the red set.

**Trap 6 — `mod.rs:896-907`'s comment is false and the arm is reachable.** It claims *"a legal-hold is impossible without an explicit reason"*, but the P29 durable-hold guard at `:471-497` fires on `reason = None` — which is exactly how `run_uninstall_cascade` calls it (`main.rs:7950`).
