## Findings (0 × P0–P2; 2 × Low, 2 × Info → all rule-10 deferred rows)

**F1 — Low (availability, cross-Spirit): one hostile guest starves every other Spirit's schedule/idle triggers for up to a day per fire.**
- `crates/maos-kernel-core/src/scheduler/schedule_watchdog.rs:300-303` — `poll_once` awaits `fire_on_schedule` inline, sequentially across all candidates.
- `crates/maos-kernel-core/src/scheduler/idle_watchdog.rs:107-126` — the JoinSet makes fires parallel *within* one tick, but `while fires.join_next().await.is_some() {}` (line 126) blocks the next tick on the slowest fire.
- `crates/maos-kernel-core/src/scheduler/hook_dispatch.rs:357-364` — `effective_cap_seconds` is the manifest's declared cap with no hard ceiling; `crates/maos-manifest/src/manifest.rs:1184-1189` admits `time_cap_seconds` up to 86,400. The code itself acknowledges the exposure (`schedule_watchdog.rs:297` "the (untrusted, up to `time_cap_seconds`) hook").
- Exploit: a third-party manifest declares `time_cap_seconds = 86400` and sleeps in `on_schedule` (or `on_idle`). One admitted hostile Spirit freezes the single watchdog task: no other Spirit's scheduled or idle trigger fires until the wall elapses; the guest stays quiescent, so `on_idle` re-fires every subsequent tick. Parallel-within-tick (the commit's claim) does not bound cross-tick stall; the schedule path is still fully sequential.
- Fix sketch: give watchdog fires a hard wall `min(declared cap, 30 s)` mirroring D-20-9-21/D-20-9-25 (`min(95% cap, 5 s/30 s)`), or detach fires from the tick (account in-flight fires separately so shutdown joins still see them). Note: the sequential-await shape predates this commit for `on_schedule`; the commit's idle change improved but did not close it.

**F2 — Low (hardening, same-user threat / concurrent writers): `write_atomic` uses a fixed, predictable temp path and a symlink-following create.**
- `crates/maos-kernel-core/src/hot_swap/archive.rs:51-62` — `path.with_extension("tmp")` yields fixed `manifest.tmp` / `snapshot.tmp`; `fs::File::create` follows a pre-planted symlink at that name (truncate-write through it, then `rename` moves the symlink over `manifest.toml`); and two concurrent writers of the same `(spirit_id, version)` share the temp path — interleaved truncate/write/rename can land mixed bytes or a `NotFound` on the loser's rename.
- Exploit reach: archive dirs are user-owned mode 0700 (`archive.rs:82-98`, `coordinator.rs:90-99`), so the symlink clobber needs a same-user process (normally out of threat model — defense-in-depth). The concurrency case is real in-process: `archive_manifest`/`archive_provisional` (`maos-bin/src/admission.rs:1597-1638`) is write-if-absent via a check-then-write TOCTOU, and a cold-swap admission racing a plain load of the same `class.name`+`version` (different text, same version) can interleave on the one temp name. Rename→dir-fsync ordering itself is correct (`archive.rs:59-62`); no gap there.
- Fix sketch: unique temp name per write (pid + monotonic counter or random suffix) created with `create_new` (O_EXCL) in a loop, optionally O_NOFOLLOW semantics; make write-if-absent atomic with `rename` from a unique temp regardless (rename-over is already the commit's semantics, per the inode test `spirit_archive_atomic_20_9.rs:10-38`).

**F3 — Info (resource amplification, operator-admitted): no cap on `[[schedule]]` entry count or `payload_b64` size beyond the 1 MiB manifest limit.**
- `crates/maos-manifest/src/manifest.rs:1904-1975` validates id/cadence/rate per entry but not `entries.len()` or decoded payload size; the manifest gate caps the file at 1 MiB (`crates/maos-bin/src/admission.rs:666`). A manifest packed with minimal entries (each `cadence_secs = 1`, `rate_limit_per_hour = 3600`) yields a first-poll burst of thousands of fires — each minting tokens, writing a TL row, and dispatching a hook — before per-pid issuance quota (`maos-capability/src/cap_quota/mod.rs:60-63`, 60k/60s) and rate buckets throttle it. Sustained rate is then bounded (see R2), so this is burst amplification of an operator-admitted manifest only.

**F4 — Info (diagnostic noise / dead-edge invariant gap): the new `eprintln!` revoke-failure path cannot actually leave a suppressed fire's token live.**
- `crates/maos-kernel-core/src/scheduler/schedule_watchdog.rs:370-387` — on a refused scope, previously minted tokens are revoked; a revoke error only warns. Traced both failure modes of `CapabilityRegistryPort::revoke` → `maos-capability/src/cap_tokens/mod.rs:294-315`: `Err(Revoked)` (already revoked by an unload/CRL racing the poll — token already dead, warning is misleading noise) and `Err(UnknownToken)` (shard miss). Shards have no capacity bound and evict only TTL-expired entries (`shard.rs:96-101`); TTL ≥ 1 s vs a microsecond mint→revoke gap, so UnknownToken for a just-minted live token is unreachable. Conclusion: the D07-A invariant ("no token minted for a suppressed fire stays live") has no credible breach here; the reachable defect is only that a benign race prints a failure-branded WARN. Optional fix: use a non-`Operator` revoke reason for this site (already-revoked returns `Ok`), or verify liveness before warning.

## Rejected candidates (investigated, no credible execution path)

1. **Cross-Spirit forced suppression.** Every mint-refusal channel in `issue_with_mediation` (`maos-kernel-core/src/capability/mod.rs:198-261`) is per-pid: paused (per-pid), policy deny (operator config, per pid+scope), context exhaustion (per-pid), issuance quota (per-pid `DashMap` slots, `cap_quota/mod.rs:246-273`); `tokens.issue` has no global cap. No Spirit can push another Spirit's schedule into `Suppressed`.
2. **Forcing a fire that should be suppressed.** Suppression is fail-closed (`schedule_watchdog.rs:242-261`: refused scope or unwired registry → no dispatch, no fire row; daemon wires `with_capability` at `maos-bin/src/main.rs:10194-10200`). Scope-free entries fire untokened by design (memory-only; effects still require per-call mediated tokens). A Spirit cannot dodge its own suppression, nor suppress-then-fire anyone else's entry.
3. **TL spam via `schedule.suppressed` rows.** The suppression path inserts `last_fire_ns` *and* consumes a rate-bucket token (`schedule_watchdog.rs:246-259`, `228-240`), bounding rows to one per max(cadence, rate) per entry; cadence ∈ [1, 604 800] and rate ∈ [1, 3600] are validated (`manifest.rs:1922-1932`); `schedule.id` is `[a-zA-Z0-9_-]{1,64}` so no intent-string injection into other writers' namespaces (no `:`/`.` possible).
4. **Provisional record forgery/staleness steering cross-major loads.** `archive_provisional`/`withdraw_provisional` (`admission.rs:1596-1623`) are only reachable from the door's cold-swap path (`spawned_lifecycle.rs:685-731`); `is_path_component` blocks traversal; withdraw only removes a directory whose `manifest.toml` the same call created (`record.exists()` precheck); a daemon death inside the start window leaving a stale record is the documented fail-closed direction, and `refuse_without_migrator` (`admission.rs:1500-1572`) refuses (never admits around) unreadable/unparseable records. Residual same-version concurrent-admission race folded into F2.
5. **Swap `NotLoaded` mid-swap abuse.** A guest cannot trigger the unload: the session outlives a child that exits after its snapshot while `swap_in_flight` (`spirit_session.rs:616-624`), and the fence is attempt-owned with walls (`spawned_lifecycle.rs:32` `ATTEMPT_WALL = 90 s`; `begin_attempt`/`end_attempt` at `:517-546` unfence on drop). The kernel path is now a typed, journaled `NotLoaded` with `DiscardSuccessor` compensation (`coordinator.rs:355-376`) where it previously panicked. Stale Arc clones of an unloaded SCB briefly carry the successor runtime but are non-Running, so no watchdog fires on them.
6. **FR4 misclassification of the new writer.** `fr4_classifier.rs:396-407` pins kind 7, token absent, prefix `schedule.suppressed:` with the exact 4-key payload of `ScheduleSuppressedRecord` (`payload.rs:36-41`); `payload_matches` requires exact key set and types (`fr4_classifier.rs:794-857`). Verified `TokenId([u8;16])` (`maos-domain/src/invariants/i1.rs:45-46`) serializes as a number array, matching the fire entry's `NumArrayOrNull` (`fr4_classifier.rs:384-393`). Both new rows classify `NonCallKernelEvent`; a forged Spirit-shaped row still classifies `Call` (exact-shape matching, token-bearing rows are calls).
7. **Serialize-failure `continue` leaks a minted token and skips the cadence stamp** (`schedule_watchdog.rs:276-285`): unreachable — `ScheduleFireRecord` is a fixed struct of string/u64/bool/array types; `serde_json::to_vec` cannot fail for it (the row-serialize `eprintln` in `payload.rs:70-72` is likewise dead). Shape note for future editors only: if that branch ever becomes live, it must stamp `last_fire_ns` and revoke `token_id` before `continue`.
8. **`unwrap`/`expect` after serde in touched code.** None in production paths: all hits are std-lock `.unwrap()`/`expect("spirits lock poisoned")` (pre-existing pattern; poison requires a writer panic under the lock) and `#[cfg(test)]` code; serde deserializations in `admission.rs` (`:639, 688, 709, 758, 1554`) are all `map_err`-typed. `check-serde-error-handling` gate green in `landing-2/gates/`.
