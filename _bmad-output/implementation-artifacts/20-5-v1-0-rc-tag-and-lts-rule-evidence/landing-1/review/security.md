## Findings (10: 1 HIGH, 4 MEDIUM, 4 LOW, 1 INFO)

**F1 — HIGH — rc-readiness "provisioning" leg omits the one provision that is actually absent: `release` environment protection.**
`xtask/src/check_rc_readiness.rs:20-24` (`PROVISIONED = [MAOS_RELEASE_PUBKEY, RELEASE_SIGNING_KEY, "fuzz-ledger branch permission"]`) vs `docs/runbooks/provisioning-checklist.md:32` (`release environment protection evidence … required before publication: required reviewers, no self-review/admin bypass, tag restrictions … ` — state **`absent`**). `release.yml:108` declares `environment: release`, which is the *only non-forgeable* barrier in the whole chain (everything in-repo is compiled from the tagged tree, see F3). The new gate audits provisioning but silently skips exactly the row that is red.
Exploit/impact: operator runs `check-rc-readiness --tag v1.0.0-rc.1`, sees all legs green (the three audited rows are `present`), tags; publication proceeds with no environment approval because none is configured — the gate actively misleads at the moment it was built for.
Fix: add the row id to `PROVISIONED` (readiness then stays honestly red until the operator provisions protection), and/or have the workflow verify `gh api repos/{repo}/environments/release` protection rules before signing.

**F2 — MEDIUM — tag-grammar bypass: anything not literally containing lowercase `-rc.` skips both new controls and lands in the "alpha" exemption.**
`.github/workflows/release.yml:119` (`if: contains(github.ref_name, '-rc.')`) and `:134-138` (`*-rc.*)` ledger required; `*-*)` ledger **not** required; `*)` required). A tag `v1.0.0-RC.1`, `v1.0.0-rc1`, or `v1.0.0-rc` skips the readiness step entirely and matches the `*-*)` arm → aggregate-only, no T3 chain, no readiness — yet still publishes as a GitHub pre-release (`prerelease: contains(github.ref_name, '-')`, release.yml:213) and looks like an rc to users. The gate binary's own grammar (`is_rc_version`, `check_rc_readiness.rs:55-62`) is stricter than the workflow's substring test, so the two disagree on edge shapes. Note `xtask/tests/release_precondition_t3_20_5.rs` pins this exact case-shape in, and `cargo run -p xtask` compiles xtask from the tagged tree, so the tag itself can even redefine the grammar (F3).
Exploit/impact: an operator typo or a tag-pusher's deliberate naming choice bypasses both release controls added by this commit.
Fix: validate the tag once, fail-closed — pass `--tag "$TAG"` to a single decision point that accepts only `^v\d+\.\d+\.\d+(-rc\.\d+)?$` (case-sensitive) and refuses any other hyphenated shape at v1+ instead of routing it to the alpha exemption.

**F3 — MEDIUM — release gates are self-hosted from the tagged ref; nothing verifies the tag points at a commit on `main`.**
`release.yml:118-143`: both new steps run `cargo run --locked -p xtask` after `actions/checkout@v5` of the *tag*, and no step checks `github.sha ∈ origin/main`. The discipline `aggregate` check-run is matched by `head_sha` only, so a PR-head SHA (checks exist without any merge/review) plus a tag pointing at it yields green "aggregate", green "readiness" (the tag's own xtask defines both), and a green T3 leg if the actor also controls ledger writes (F4). The runbook (`docs/release/tag-procedure.md` step 1) does the `origin/main` tip check manually; the workflow does not.
Exploit/impact: any actor with tag-push rights can publish an arbitrary, unreviewed SHA that passes every in-workflow rail; the only true barrier is the release environment — currently unprovisioned (F1).
Fix: first `sign-and-publish` step: `git fetch origin main && git merge-base --is-ancestor "$GITHUB_SHA" origin/main`; ideally run the gate binary from a reusable workflow pinned to `main`, not from the tag.

**F4 — MEDIUM — the T3 chain's trust anchor is an unsigned JSON file on a mutable branch, writable via `GITHUB_TOKEN` fallback.**
`.github/workflows/release.yml:140` fetches `contents/fuzz-ledger.json?ref=fuzz-ledger`; the producer (`fuzz-prerelease.yml:304`) pushes with `token: ${{ secrets.FUZZ_LEDGER_WRITE_TOKEN || secrets.GITHUB_TOKEN }}` under job `permissions: contents: write` (`fuzz-prerelease.yml:13-15`). Records carry self-reported `cpu_seconds`; nothing links them to an actual workflow run. Anyone who can dispatch `fuzz-prerelease` (write-access actors; the workflow is `workflow_dispatch`-only and dispatches at any ref) or push the branch can append five fabricated T3 records for any SHA and green the leg. Branch protection for `fuzz-ledger` is unobservable from the repo, and the readiness "fuzz-ledger branch permission" leg merely re-reads a committed checklist row — circular (F8).
Exploit/impact: forged 24 h×3-target evidence accepted by `check_t3_fuzz_chain` (`xtask/src/check_release_precondition.rs:63-110`), defeating the NFR-Sec-5/6 release precondition.
Fix: verify the ledger tip commit's signature (`gh api repos/…/commits/fuzz-ledger --jq .commit.verification.verified`), or have the gate cross-check each `run_id` prefix against a real completed `fuzz-prerelease` run (`gh run view <id> --json conclusion,headSha,workflowName`); drop the `GITHUB_TOKEN` fallback so only the provisioned identity can write.

**F5 — MEDIUM — deny.toml's stated invariant is now false, and the new deny leg is class-blind.**
`deny.toml:16-18` header: "All entries below are `unmaintained` advisories (NOT `vulnerability` class) … none masks a security vulnerability" — contradicted by `deny.toml:55-62`: `RUSTSEC-2026-0459` is bundled-SQLite **CVE-2026-119375** (vulnerability class). The new `deny_leg` (`xtask/src/check_rc_readiness.rs:126-160`) only checks that each ignored id appears in a bullet/row of `deferred-work.md` (`line.contains(id)`, substring, `:144-148`) — it cannot distinguish vulnerability-class ignores, and a substring id match is spoofable.
In-use exposure of 0459 [assessed, partly INFERENCE]: all production `Connection::open` sites I surveyed (maos-audit `backup.rs`, maos-bin `enterprise_identity.rs:423`, `purge.rs:1911`) open maos-created transparency-log/audit DBs, so the "only maos-written databases" claim holds for file *creation* — but `payload_redacted` rows carry spirit-influenced bytes, so a content-triggered SQLite parser bug would be reachable second-order. CVE specifics are repo-internal 2026 data I cannot verify externally.
Fix: have `deny_leg` consume `cargo deny check advisories --json` and refuse any ignore whose advisory class is `vulnerability`; exact-token match the deferred row; rewrite the false header. Also note `[graph] targets` covers only the two Linux triples while the release also ships `aarch64-apple-darwin` (darwin-only dep advisories are unchecked).

**F6 — LOW — aggregate check-run race: `status=completed&filter=latest` can surface an older green run.**
`release.yml:142` + `xtask/src/check_release_precondition.rs:142-152`. The query pre-filters on `status=completed`; if the newest `aggregate` run for the SHA is re-running (in progress), the API can return the previous completed green run, bypassing the code's own "never search for any success" invariant (`:143-147`).
Fix: drop `status=completed` from the query; the code already refuses non-`completed` status.

**F7 — LOW — LTS clock record accepts rc-shaped tags, contradicting the published policy.**
`xtask/src/stability_matrix.rs:388-391`: `clock_start_tag` only checks a charset (`alnum . - _`), so a GA record naming `v1.0.0-rc.9` (or any tag) renders an LTS clock-start in STABILITY.md while the generated policy says an rc "never starts the clock" (`stability_matrix.rs:225-231`, `docs/release/lts-policy.md`). Trust = repo committer, so impact is doc-integrity, but this is the file that publishes the support-window claim.
Fix: reject pre-release-shaped tags (and, until a v1.5 line exists, require `clock_start_tag == "v1.0.0"`).

**F8 — LOW — readiness legs audit committed docs inside the same tree the tag carries (circular assurance).**
`check_rc_readiness.rs:66-92` (sprint-status), `:95-124` (checklist rows), `:126-160` (deferred-work): a committer — or F3's off-main tag — satisfies every leg by editing markdown. The docs are honest that the operator lane owns them, but the gate presents them as enforcement. Fix: source operator-lane facts out-of-band (`gh api` environments/branch-protection/secrets existence) where the token allows.

**F9 — LOW — release-path actions pinned by mutable tags.**
`release.yml:60,101,117,144` (`checkout@v5`, `dtolnay/rust-toolchain@v1`, `Swatinem/rust-cache@v2`, `upload/download-artifact@v4`, `setup-qemu@v3`) and `fuzz-prerelease.yml:56,304` — all tag refs; only `softprops/action-gh-release@3bb1273…` is SHA-pinned, so the convention exists. A hijacked `Swatinem/rust-cache@v2` runs inside `sign-and-publish` where the job token holds `contents: write` and steps handle `RELEASE_SIGNING_KEY`. Pre-dates this commit but is load-bearing for the new chain. Fix: SHA-pin every action in both workflows.

**F10 — INFO — schema-peel typing quirk (no security impact).**
`crates/maos-manifest/src/manifest.rs:4654-4677`: a non-table `[cli_wrapper]` value (string/array, incl. `[[cli_wrapper]]`) is treated as "absent" → `Ok(1)`; refusal then happens later as a generic strict-parse type error instead of the typed `ECliWrapperSchemaUnsupported`. Fail-closed either way; window is `1..=1` (`maos-spirit-abi/src/lib.rs`), so discarding the peeled value at the call site (`worker_spawn.rs:615`) is correct today but should assert the version once a v2 window opens.

## Rejected candidates (9)

1. **Env vars disabling the gates** — neither gate reads any env var (no `env::var` in either file; only `evidence_ledger.rs` reads `GITHUB_ACTIONS`, a different gate). `release.yml` `workflow_dispatch` defines no inputs and `sign-and-publish` requires `event == 'push'` → dispatch/PR rehearsal cannot publish.
2. **Seconds summed across runs** — correctly prevented: per-run link map, duplicate link takes `max`, cross-run never summed (`check_release_precondition.rs:70-105`), locked by test `two_runs_each_below_24h_never_sum_across_runs`.
3. **`gh api` pagination/truncation** — `check_name=aggregate&filter=latest` yields ≤1 run per name (default page size ample); `tag-procedure.md` documents exactly why the filter is mandatory (161 discipline jobs). Ledger fetch uses the raw media type (≤100 MB raw support; ledger is KBs); read/parse errors fail closed.
4. **`run_id` hyphen stitching** — `rsplit_once('-')` cannot merge links across distinct runs without ledger write access (covered by F4); format matches the collector's `<run>-<link>`.
5. **Ledger record-format injection** — strict serde structs (`schema_version: u32`, five typed fields); no shell/SQL sink for record fields.
6. **Peel panic/DoS/confusion** — non-integer, zero, negative, oversized, float, unicode-literal, nested-table and array values are all refused typed; error text bounded to 64 chars (`declared.to_string().chars().take(64)`); TOML rejects duplicate keys; huge integer literals fail at parse; homoglyph keys remain for `deny_unknown_fields`. Test vectors (`crates/maos-manifest/tests/cli_wrapper_schema_20_5.rs`) cover the classes.
7. **unwrap/expect after serde** — none in touched production paths (only `#[cfg(test)]` fixtures); all serde/toml errors in `check_rc_readiness.rs`, `check_release_precondition.rs`, `manifest.rs` are `map_err`'d.
8. **LTS docs as exploitable promises** — the rc line explicitly carries *no* commitment and no end-of-support date is published (`lts-policy.md`), removing the classic premature-EOL/over-promise abuse; generated STABILITY.md is drift-checked. Only F7's validation gap remains.
9. **TOCTOU between check and tag** — both gates re-run at tag-push on the tag SHA and the runbook re-reads `candidate_sha` after rehearsal; the ledger is keyed by exact SHA. The residual is tag↔main ancestry (F3), not a time window.
