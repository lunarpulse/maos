- 1. **`handle_option_pick` silently consumes the notification on invalid option, then returns a misleading error.** The `.lock().take()` removes the notification *before* matching the option character. When the caller passes anything other than `'a'`, `'b'`, or `'c'`, the pending notification is permanently lost and the error says "no pending notification" — which is false. The real problem is an invalid option, not a missing notification.
- 2. **All four MCP servers (calendar, slack, linear, figma) are wired to the single calendar transport URI.** The `--live` block reads `_slack_uri`, `_linear_uri`, `_figma_uri` into underscore-prefixed (unused) bindings and never creates transports for them. All four `McpServerEntry` records share the one `StreamableHttpTransport` built from `MAOS_MCP_CALENDAR_URI`. Slack, Linear, and Figma calls will hit the calendar endpoint — a functional bug masked by the underscore suppressions.
- 3. **`LiveButlerMcpPort` is constructed with `spirit_pid: 0` and a zeroed `posture_hash`.** These are security-sensitive fields that the capability registry uses to issue and validate tokens. Zeroed values mean every MCP call is token-issued under a fake identity. If the registry validates these fields, the calls will fail at runtime; if it doesn't, the audit trail is falsified.
- 4. **`handle_option_pick` does not actually call `mcp_port.write_linear_note()` for option 'a'.** The AC2 spec requires a real `linear.create_issue` MCP call. The implementation sets `linear_note_written: true` and returns a message string, but the Linear write never happens — neither here nor in any caller. The unit test only asserts the flag, not the MCP call. This is a stub labeled as a real feature.
- 5. **JB-3 test uses `cargo run -p maos-bin` instead of the pre-compiled `CARGO_BIN_EXE_maos`.** The companion `butler_8_14b.rs` correctly uses `env!("CARGO_BIN_EXE_maos")` for an instant subprocess spawn. JB-3 compiles on every invocation, making it orders of magnitude slower and non-deterministic in CI. This is an inconsistency that will cause CI timeout flakiness.
- 6. **`block_on_sync` panics on `Poll::Pending` — a latent runtime bomb with a known detonation date.** The story itself notes that "8.14c real HTTP transport" will make MCP calls truly async over the network. When that lands, `block_on_sync` will panic on every `on_idle` cycle. There is no comment, feature flag, or compile-time guard marking this as prototype-only — the next developer will inherit a production panic path.
- 7. **The shell test `shell_butler_pick_renders_option_messages` is inherently racy.** It pipes four commands to stdin, drops stdin (EOF), then immediately reads stdout. There is no synchronization mechanism (no prompt-wait, no sleep, no line-reading protocol). On a slow CI runner, the shell may not have processed all four inputs before the parent reads stdout, causing intermittent assertion failures.
- 8. **`maos-shell` now directly depends on the `butler` spirit crate, coupling a generic shell to a specific spirit.** The shell is supposed to dispatch generically (load any spirit by manifest). Hard-coding `butler` as a dependency means every future spirit that needs shell-level dispatch will require editing `maos-shell/Cargo.toml` — this is the tight-coupling antipattern the architecture is designed to avoid.
- 9. **`maos-bin/Cargo.toml` specifies `async-trait = "0.1"` as a direct version string, while the story's FORK 1 locked implementation and the `butler/Cargo.toml` use workspace inheritance (`{ workspace = true }` style or consistent specification).** The inconsistency means `maos-bin` and `butler` could resolve to different `async-trait` versions, and the deviation from the workspace convention makes future version bumps harder to coordinate.
- 10. **`FakeButlerMcpPort` is declared `pub mod test_support` but gated behind `#[cfg(test)]`, so the `pub` visibility is vacuous.** No external crate (including `maos-bin`'s integration tests) can reference it. The `write_linear_call_count` atomic counter exists but is never asserted in any test — `handle_option_a_calls_linear_write` checks the outcome flag, not whether `FakeButlerMcpPort.write_linear_note` was actually invoked, making the counter dead instrumentation.
- 11. **The `drivers` module in `maos-mcp` is unconditionally compiled and exposes butler-specific helpers from a generic crate.** `pub mod drivers` has no feature gate, so every consumer of `maos-mcp` pays for butler-specific arg builders and response parsers. When researcher/other spirits get their own drivers, the module will grow unbounded. A feature flag or separate crate would prevent this accumulation.
- 12. **`extract_content` borrows `&McpResponse` and then clones `response.content`, but the caller owns the response and could pass ownership instead.** The function should take `McpResponse` by value to avoid an unnecessary clone on every MCP call — these are per-`on_idle` allocations that compound in long-running daemon sessions.
